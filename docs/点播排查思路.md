# 点播排查思路

## 1. 文档目标

这份文档只解决两类问题：

- 首页卡片为什么没有显示真实封面，还是占位图
- 前端上传后，视频为什么没有顺利进入点播链路

这里优先采用最短排查链，不先展开大范围分析。
目标是尽快判断问题落在哪一层：

- API 返回的数据不对
- `/image/...` 或 `/vod/...` 地址不可访问
- MinIO 里没有对象
- Qt 前端没有请求到数据
- Qt 前端已经请求到数据，但当前运行的不是最新版本
- 上传接口成功了，但 worker 没有继续处理

---

## 2. 当前正确链路

当前项目里的点播链路应该是：

1. `HomePage` 请求 `GET /api/videos`
2. API 返回每个视频的 `coverUrl` 和 `playUrl`
3. `coverUrl` 应该指向 API 自己的 `/image/...`
4. `playUrl` 应该指向 API 自己的 `/vod/...`
5. Qt 前端再去请求这两个地址
6. API 代理读取 MinIO 对象并返回给前端

也就是说，前端期望拿到的地址应该像这样：

```text
http://192.168.99.128:8080/image/video/1/cover.jpg
http://192.168.99.128:8080/vod/video/1/hls/index.m3u8
```

而不是：

```text
http://192.168.99.128:9000/image-assets/video/1/cover.jpg
http://192.168.99.128:9000/vod-media/video/1/hls/index.m3u8
```

原因很简单：

- `9000` 是 MinIO S3 API
- `9001` 是 MinIO Console
- `8080` 才是项目自己的业务 API

前端应该优先走 `8080`，由 API 去代理读取 MinIO 对象。

---

## 3. 封面最短排查链

### 3.1 第一步：先确认列表接口里有没有正确的 `coverUrl`

在虚拟机里执行：

```bash
curl http://127.0.0.1:8080/api/videos
```

重点看返回里的每个视频项是否带了：

```json
"coverUrl": "http://192.168.99.128:8080/image/video/1/cover.jpg"
```

如果这里就没有 `coverUrl`，或者还是旧的 `:9000/image-assets/...`，问题不在前端，先排查下面几项：

- 你跑的可能还是旧版 API
- `PUBLIC_BASE_URL` 配置不对
- 数据库里封面字段为空

这一步的结论：

- `coverUrl` 正确：继续下一步
- `coverUrl` 错误：先修 API，不要继续看 Qt

---

### 3.2 第二步：直接访问 `coverUrl`

把 `coverUrl` 单独拿出来访问。

在虚拟机里执行：

```bash
curl -I http://127.0.0.1:8080/image/video/1/cover.jpg
```

在 Windows 宿主机上也可以直接在浏览器打开：

```text
http://192.168.99.128:8080/image/video/1/cover.jpg
```

预期现象：

- 返回 `200`
- `Content-Type` 类似 `image/jpeg` 或 `image/png`
- 浏览器里能直接看到图片

如果这里访问失败，说明问题还没到 Qt 渲染层。

常见结论：

- `404`：API 找不到对应对象，继续看第 3 步
- `500`：API 代理读取 MinIO 失败
- 超时或无法访问：宿主机到虚拟机网络不通，或者 API 没监听正确地址

---

### 3.3 第三步：确认 MinIO 里是否真的有封面对象

打开 MinIO Console：

```text
http://192.168.99.128:9001/browser/image-assets
```

进入 `image-assets` bucket，检查是否存在：

```text
video/1/cover.jpg
```

这个页面的意义只是“看桶里有没有对象”，不是给前端用的播放或加载地址。

如果 MinIO Console 里没有这张图，说明不是前端问题，通常是：

- worker 没有生成封面
- worker 生成了封面，但上传 `image-assets` 失败
- 数据库写了 `cover_object_key`，但对象实际不存在

如果 MinIO Console 里有这张图，但 `/image/video/1/cover.jpg` 仍然失败，说明问题在：

- API 到 MinIO 的读取链路
- MinIO 配置
- bucket 名配置错误

---

### 3.4 第四步：确认前端有没有拿到这个地址

当前首页逻辑是：

1. `HomePage::handleFeedReply(...)` 解析 `coverUrl`
2. `HomePage::requestCardCover(...)` 发起图片请求
3. `VideoCard::setPosterPixmap(...)` 更新卡片封面

相关代码位置：

- `frontend/pages/HomePage/HomePage.cpp`
- `frontend/components/VideoCard/VideoCard.cpp`

如果前 3 步都没问题，但卡片还是占位图，就要重点怀疑：

- 当前运行的前端不是新编译出来的版本
- Qt 请求图片失败但没有直接暴露到界面
- 图片数据拿到了，但没有成功解码

---

### 3.5 第五步：确认当前运行的是新前端

如果代码已经改过，但界面效果没变，先不要继续猜。
先重新编译并重新启动前端。

当前仓库里可用的编译方式：

```powershell
& 'D:\itffmpeg\x86_64-15.2.0-release-posix-seh-ucrt-rt_v13-rev1\mingw64\bin\mingw32-make.exe' -C build QtFrontend
```

如果是整个前端程序需要重启，就重新启动当前正在运行的 `QtFrontend.exe`。

这一步常见现象：

- 代码已经正确，但旧进程还在跑旧版本
- 静态库编过了，但可执行程序没重启

---

## 4. 上传链路

### 4.1 一句话理解

当前前端上传不是直接把文件传到 MinIO。

当前实际链路是：

- Qt 客户端先通过 HTTP 把文件传给 API
- API 再代表客户端把原视频写入 MinIO 的 `raw-media`
- API 再写数据库和转码任务
- worker 再从 MinIO 取原视频做转码和封面生成

---

### 4.2 最短时序图

```text
Qt UploadPage
  -> POST /api/videos/upload

API server
  -> save temp file on VM
  -> upload raw file to MinIO raw-media
  -> insert videos row
  -> insert transcode_jobs row
  -> set video status = queued

Worker
  -> pick pending job
  -> set video status = processing
  -> download raw video from MinIO
  -> ffmpeg transcode to HLS
  -> generate cover.jpg
  -> upload HLS to MinIO vod-media
  -> upload cover to MinIO image-assets
  -> set video status = ready

API server
  -> expose /api/videos /api/videos/{id} /vod/... /image/...

Qt HomePage
  -> refresh feed
  -> read status / coverUrl / playUrl
```

---

### 4.3 这条链路里每一层在做什么

- `UploadPage`
  选择本地文件，填写标题和描述，然后发起 `multipart/form-data` 上传请求

- `POST /api/videos/upload`
  接收客户端上传的文件，保存到虚拟机临时目录，并复用后端导入逻辑

- `MinIO raw-media`
  存原始视频文件，不直接给前端播放

- `videos`
  保存视频主记录，比如标题、状态、对象路径、封面路径、播放路径

- `transcode_jobs`
  保存待处理转码任务，供 worker 消费

- `worker`
  常驻轮询任务，把原视频转成 HLS 并生成封面图

- `MinIO vod-media`
  存 HLS 播放产物

- `MinIO image-assets`
  存封面图

- `GET /api/videos`
  给首页列表返回视频状态、封面地址和播放地址

- `/image/...` 和 `/vod/...`
  由 API 代理读取 MinIO 对象，再返回给前端

---

### 4.4 为什么前端不是直接传 MinIO

当前这样设计的好处是：

- 前端不需要持有 MinIO 凭据
- 前端不需要理解 bucket 和对象路径
- API 可以统一做入库、排队、状态管理
- 以后更容易加鉴权、大小限制、类型校验、上传审计

这也是当前阶段更稳的方案。

---

### 4.5 看到上传成功后，系统里通常发生什么

如果上传成功，接口一般会先返回：

- 新的视频 `id`
- 新的转码任务 `jobId`
- `status = queued`

然后 worker 会把它推进到：

- `processing`
- `ready`

如果失败，则通常会停在：

- `failed`

所以“上传成功”不等于“已经可以播放”，它只表示：

- 文件已经进系统
- 转码任务已经创建

---

### 4.6 上传问题应该先看哪一层

可以按这个顺序判断：

- 前端点上传后立刻报错
  优先看 Qt 是否真的请求到了 `/api/videos/upload`

- `curl -F ... /api/videos/upload` 都失败
  优先看 API 上传接口

- 上传接口成功，但视频一直是 `queued`
  优先看 worker 是否常驻运行

- 状态到了 `processing` 但最后变成 `failed`
  优先看 worker 日志、`ffmpeg`、MinIO 写入和数据库错误信息

- 状态到了 `ready` 但前端看不到封面或不能播放
  再回到本文前面的封面 / 点播排查链继续查

---

## 5. 一眼判断表

可以按下面这个顺序快速判断：

- `/api/videos` 里没有 `coverUrl`
  说明 API 或数据本身有问题

- `/api/videos` 里有 `coverUrl`，但访问 `/image/...` 失败
  说明 API 代理图片链路有问题

- `/image/...` 能打开，但 MinIO Console 里没有对象
  说明对象路径和数据库记录可能不一致，或者你看的不是当前真实数据

- MinIO Console 里有对象，`/image/...` 也能打开，但卡片还是占位图
  说明问题大概率在 Qt 前端请求或前端版本

- 上传接口成功，但视频长时间停在 `queued`
  说明 worker 没有常驻运行，或者没有成功抢到任务

- 重新编译并重启前端后恢复正常
  说明之前跑的是旧版本

---

## 6. 当前项目里这几个地址分别是什么

- `http://192.168.99.128:9001/browser/image-assets`
  MinIO Console，用来查看 `image-assets` 桶里有没有封面文件

- `http://192.168.99.128:9000/...`
  MinIO S3 API，给后端或工具程序访问对象存储用，不建议前端直接依赖

- `http://192.168.99.128:8080/image/...`
  项目 API 代理出来的图片地址，前端应该使用这个

- `http://192.168.99.128:8080/vod/...`
  项目 API 代理出来的点播地址，前端播放应该使用这个

- `http://192.168.99.128:8080/api/videos/upload`
  项目 API 提供的上传入口，前端通过这个地址把视频先交给服务器

---

## 7. 推荐排查顺序

针对当前项目，建议每次都按这个顺序查：

1. `curl http://127.0.0.1:8080/api/videos`
2. 找到目标视频的 `coverUrl`、`playUrl`、`status`
3. 在浏览器里打开 `coverUrl` 或 `playUrl`
4. 打开 `http://192.168.99.128:9001/browser/image-assets` 或对应 bucket 看对象是否存在
5. 确认 worker 正在常驻运行
6. 重新编译并重启 Qt 前端

只要这几步里哪一步失败，就先停在那一层处理，不要同时怀疑所有模块。
