# 直播卡顿修复

## 1. 最新现象

当前直播观看主链路已经打通，而且当前代码已经不再是“解到就直接画”的最早版本了。

现在已经具备的最小能力是：

- `HttpFlvStreamReader` 持续收 HTTP-FLV 字节流
- `FlvDemuxer` 增量拆出 FLV tag
- `LiveVideoDecodeWorker` 持续做 H.264 解码
- `VideoFrameQueue` 缓存已解码视频帧
- `QTimer` 以固定 tick 驱动纯视频渲染
- `currentTargetVideoPtsMs()` 用墙钟计算目标显示时间
- `dropLateQueuedVideoFrames()` 丢掉明显迟到的旧帧

但实际观看时，仍然会出现下面这类卡顿：

- 首帧能出来
- 画面能短暂动一下
- 然后停在某一帧不继续往下播
- 过一阵可能又恢复一下，然后再次卡住

这说明当前问题已经不是：

- 服务端没推流
- HTTP-FLV 没连通
- FLV 解析失败
- FFmpeg 没解出 `AVFrame`

而是：

- 纯视频播放时钟和突发到包的节奏没有对齐好
- 队列溢出后的策略还不够稳定

---

## 2. 先把当前真实数据流说清楚

这次排查一定要先把“当前版本到底走到哪一层了”说清楚，否则很容易还停留在旧认知里。

当前 Qt 直播观看链路实际上是：

```text
QNetworkReply::readyRead()
-> HttpFlvStreamReader::handleReadyRead()
-> QByteArray chunk
-> LivePlayerSession::handleReaderDataChunk()
-> FlvDemuxer::pushBytes()->parseFlvHeader(report)
-> FlvTag(video)
-> enqueueVideoTag()
-> LiveVideoDecodeWorker
-> FlvVideoDecoder / FFmpeg H.264 decode
-> handleWorkerDecodedVideoFrame()
-> VideoFrameQueue
-> onRenderTick()
-> currentTargetVideoPtsMs()
-> tryRenderNextQueuedVideoFrame()
-> handleDecodedVideoFrame()
-> VideoOpenGLWidget::presentFrame()
-> QOpenGLWidget::update()
-> VideoOpenGLWidget::paintGL()
```

也就是说，当前版本已经有了最小版的：

- 视频帧队列
- 视频播放时钟
- render tick
- 迟到帧丢弃

但还没有真正做完整的：

- 启播缓冲策略
- 突发到包下的时钟重锚定
- 抖动缓冲
- 音频解码 / 音频输出
- A/V sync

这也是为什么现在已经比“直接收到帧就画”更进一步了，但仍然可能出现“只停一帧”的卡住现象。

---

## 3. 这次排查思路

这次排查不是直接猜“是不是 OpenGL 有问题”，而是按数据流一层层排。

### 3.1 先确认不是源头问题

先看 `live_watch.log` 是否出现：

- `state=Connecting`
- `state=Reading`
- `HTTP connected (video/x-flv, status 200)`
- `FLV header validated`

如果这些都没出现，优先排服务端、URL、HTTP-FLV 映射。

如果这些都出现了，说明：

- Qt 已经拿到 HTTP 响应
- FLV header 已通过
- 字节流已经持续送进 demux

### 3.2 再确认不是解码器问题

再看日志是否出现：

- `first decoded frame ready`
- `receive worker frame pts=...`
- `first frame queued pts=...`
- `first frame submitted to render pts=...`

如果这些都出现，说明：

- sequence header 已进 FFmpeg
- FFmpeg 已持续产出 `AVFrame`
- session 已把解码后的帧送进 `VideoFrameQueue`
- render tick 也确实开始工作

### 3.3 最后盯住 render 侧的三个量

这次最关键的不是“有没有帧”，而是同时看下面三个量：

- `targetPts`
- `frame_queue` 队首帧的 `pts`
- `drop oldest on overflow` / `wait frame`

如果出现这种组合：

- 解码线程持续在产出新帧
- `frame_queue` 持续 overflow
- render 侧持续打印 `wait frame pts=... targetPts=... earlyMs=...`

那么就不是“没帧可画”，而是“队列里全是未来帧，当前时钟还没走到这些帧的显示时刻”。

---

## 4. 这次日志里真正说明了什么

下面是这次定位最关键的几段现象。

### 4.1 首帧阶段是正常的

日志里先出现：

- `first frame queued pts=43`
- `targetPts=52`
- `show frame pts=43 targetPts=52 lateMs=9`

这说明最开始的时钟基准和首帧显示是对得上的。

### 4.2 但解码侧很快就“追过头”

同一时刻还能看到：

- worker 在快速 `dequeue tag_ts=... depth_after=86`
- session 持续 `receive worker frame pts=...`
- `frame_queue` 很快开始 `drop oldest on overflow`

这说明：

- `readyRead()` 不是均匀一帧一帧到，而是一次推来一大批字节
- demux 一次性拆出很多 tag
- worker 又很快把这些 tag 解成帧
- 解码速度在这一小段时间里明显快于“真实播放速度”

### 4.3 队列被“未来帧”占满后，render 只能一直等

这次最关键的日志信号是：

```text
targetPts=100
wait frame pts=127 targetPts=100 earlyMs=27

targetPts=230
wait frame pts=694 targetPts=230 earlyMs=464

targetPts=3579
wait frame pts=6217 targetPts=3579 earlyMs=2638
```

这几行合起来的含义是：

- 当前播放时钟只走到 `targetPts`
- 但队首帧已经跳到了更靠后的 `pts`
- render 线程按当前逻辑不能显示“未来帧”
- 它只能不断等待

而用户看到的效果就是：

- 屏幕停留在上一张已经画出来的帧
- 看起来像“画面只停一帧，不会往下播”

### 4.4 为什么队首帧会越来越靠后

因为 `VideoFrameQueue` 目前上限是固定深度：

```cpp
VideoFrameQueue::kDefaultMaxDepth = 10;
```

一旦 producer 继续比 consumer 快，就会不断发生：

```text
drop oldest on overflow pts=...
```

这意味着当前策略更像是：

- 队列满了就丢最老的
- 保留最近解出来的 10 帧

问题在于：

- 当前保留下来的这 10 帧，很可能已经整体“跑到未来去了”
- render 又严格按 `queuedFrame.ptsMs > targetPtsMs` 时等待

于是就形成了这个卡住机制：

```text
最后一张已经显示的帧停在屏幕上
-> 队列里的帧都比当前 targetPts 超前
-> render 只能 wait
-> 新帧继续进来时，旧帧又被 overflow 丢掉
-> 屏幕仍然保持最后那一张
```

这就是“为什么会停留一帧”的直接原因。

## 5. 当前根因，不是“没有时钟”，而是“时钟基准和突发追帧策略还不对”

旧版本的结论可以概括为“没有 frame queue / 没有 clock”。

但对当前代码来说，这个结论已经不准确了。

当前更准确的结论是：

### 根因 1：启播后很快收到一大批历史帧

HTTP-FLV 在 `readyRead()` 下会批量到包，不会保证天然匀速。

于是：

- demux 会在很短时间内吐出很多视频 tag
- worker 会在很短时间内解出很多视频帧
- 帧队列会迅速冲满

### 根因 2：播放时钟只在“首帧入队”时锚定一次

当前代码在第一次入队时：

```cpp
firstQueuedVideoPtsMs_ = ptsMs;
playbackStartWallClock_ = std::chrono::steady_clock::now();
```

后面 `targetPts` 一直按：

```cpp
targetPts = firstQueuedVideoPtsMs_ + elapsed
```

来算。

这个思路在“到包比较平稳”时是可行的，但在“首帧之后立刻 burst 解出很多后续帧”时，`targetPts` 很容易追不上队列前沿。

### 根因 3：当前只有“迟到帧丢弃”，没有“未来帧追赶 / 重锚定”

现在已经有：

- `dropLateQueuedVideoFrames(targetPtsMs)`

它解决的是：

- 队首帧已经明显落后于当前时间

但它没有解决：

- 队列里的帧整体跑到当前时钟前面太多

所以当前逻辑能处理“太晚”，却还不擅长处理“整体太早”。

---

## 6. 为什么 `ffplay` 更顺

`ffplay` 的优势不是“只是解码更快”，而是它对“什么时候该播哪一帧”这件事处理得更完整。

它通常会把这些事一起考虑：

- demux queue
- packet queue
- frame queue
- 启播缓冲
- 视频时钟
- 音频时钟
- A/V sync
- 落后时丢帧
- 超前时等待
- 必要时重新校正时钟

而当前 Qt 版本虽然已经迈出了：

- frame queue
- render tick
- targetPts

这一步，但还没把“突发到包后的重新追平策略”补完整。

---

## 7. 现在应该怎么排这种问题

以后再遇到“画面卡住 / 只停一帧”的直播问题，可以按下面顺序排。

### 7.1 第一层：先确认有没有流

看这些日志：

- `state=Connecting`
- `state=Reading`
- `HTTP connected`
- `FLV header validated`

没有这些，先排服务端和 URL。

### 7.2 第二层：再确认有没有持续解码

看这些日志：

- `first decoded frame ready`
- `receive worker frame pts=...`
- `dispatch decoded frame to session pts=...`

如果这些还在持续增长，说明不是“解码停了”。

### 7.3 第三层：看是不是 render 卡在等未来帧

重点看这些日志组合：

- `drop oldest on overflow`
- `targetPts=...`
- `wait frame pts=... targetPts=... earlyMs=...`

如果：

- `earlyMs` 长时间为正，而且数值很大
- `drop oldest on overflow` 还在持续发生

就要优先怀疑：

- 队列前沿跑到了未来
- 当前播放时钟落后于队列
- 屏幕只是被上一张已显示帧“卡住”

### 7.4 第四层：区分“没画出来”和“没有该画的时机”

如果 render 侧反复打印的是 `wait frame`，那不是“没有帧”，而是：

- 有帧
- 但按当前时钟判断，这些帧还不该显示

这个区分非常关键。

## 9. 这轮结论的一句话总结

当前“只停留一帧”的直接原因不是没解码，也不是没收到流，而是：

> 解码侧在 burst 到包时把帧队列快速推到了未来，队列又因为 overflow 不断丢掉旧帧，而播放时钟还按首帧基准慢慢走，render 线程于是长期判定“还没到这些帧的显示时间”，屏幕就只剩最后一张已显示帧不动。

---

## 10. 如何验证修复是否真的有效

不要只看“有没有画面”，要重点看“是否还会停在一帧上不动”。

建议按下面顺序验证：

1. 保持 `ffmpeg -> RTMP -> SRS -> HTTP-FLV` 链路不变
2. 用同一路流同时对比 `ffplay http://...flv`
3. Qt 客户端连续观看至少 30 秒
4. 观察日志里是否还会大量出现：
   - `drop oldest on overflow`
   - `wait frame pts=... targetPts=... earlyMs=...`
5. 重点看：
   - `earlyMs` 是否长期几百毫秒到几秒
   - `frame_queue depth` 是否长期钉死在上限
   - 是否还会出现“屏幕停一帧不动，但解码日志仍在继续”

修复后更理想的现象应该是：

- `frame_queue depth` 在一个小范围内波动
- `queue.front().pts` 和 `targetPts` 的差值可控
- `wait frame` 只偶尔出现，不会长时间连续刷屏
- 主观观感上不再出现明显“停一帧”

## 11. 接入音频后的新一轮定位补充

上面 1 到 10 节主要是在“纯视频直播链路”阶段做的定位和修正。

当前项目已经继续往前走了一步：

- FLV 音频 tag 已经进入 live watch 主链路
- AAC 已经可以解码成 PCM
- PCM 已经送到 SDL 音频设备播放
- 已经建立了最小 `audio clock`
- render tick 仍然保留，但 `targetPts` 可以切到跟随 `audio clock`

这意味着：

- 现在的卡顿，已经不能再只按“纯视频时钟”去看
- 也不能只看“有没有 decode 出视频帧”
- 必须同时看音频时钟、音频缓冲、视频队列保留策略、视频解码速度

### 11.1 这次新的关键现象

这次日志里出现了一个和纯视频阶段不同的现象：

- 音频已经连续播放
- `audio clock` 在稳定推进
- 视频 decode worker 也还在持续解码
- 但是很多“已经解码成功的视频帧”在 session 入队后又被 future trim 提前丢掉
- 最后 render 线程只能长期 `wait_frame`

也就是说，这次不是：

- 服务端没推流
- demux 没拆出 tag
- FFmpeg 没解码出视频帧

而是：

- 视频帧“解出来了”
- 但相对于当前音频时钟看起来“太超前”
- 于是被过早裁掉
- 等真正播放时间走到那里时，那一段连续视频已经缺失了
- render 只能继续等更后面的下一批幸存帧

这类问题本质上是：

> 音频主时钟已经建立，但视频 future-frame 保留策略还是沿用了纯视频阶段的思路，导致“同步主时钟”和“队列保留策略”不匹配。

### 11.2 为什么这次不能继续激进丢 future frame

纯视频阶段里，适当裁掉未来帧有时可以控制 burst。

但在已经切到 `audio master` 之后，要特别小心：

- 当前时刻“超前于 audio clock 的帧”并不等于“无用帧”
- 它们往往就是接下来几百毫秒到几秒内马上要显示的连续帧
- 如果把它们提前裁掉，后面视频时间轴就会出现空洞
- 空洞一旦出现，render 线程就只能长时间停在最后一帧已显示画面上

所以这里要明确区分两类丢帧：

1. 丢“明显迟到的旧帧”

- 这是合理的
- 因为这些帧已经错过显示时机
- 不丢反而会拖慢追赶

2. 丢“未来帧”

- 只能作为异常恢复手段
- 不能作为 steady state 的常规策略
- 尤其不能在音频缓冲很厚、音频时钟还没追上来时，把后面连续视频一段一段裁空

结论是：

> 在 `audio master` 下，正常策略应该是“保住未来连续帧，限制解码速度”，而不是“解得快了就先把未来帧删掉”。

### 11.3 这次不是“音频和视频读包速度不同”这么简单

从网络读取角度说，HTTP-FLV 仍然只有一条字节流：

`QNetworkReply::readyRead() -> QByteArray chunk -> FlvDemuxer`

所以并不是“音频走一条网络、视频走另一条网络”，也不是简单的“音频包读得更快”。

真正不同的是后面的三件事：

1. 音视频 tag 的天然节奏不同

- AAC tag 通常更小、更密
- H.264 video tag 通常更大、更突发

2. 音视频下游消费方式不同

- 音频是 decode 成 PCM 后被 SDL callback 持续消耗
- 视频是 decode 成帧后进入 `VideoFrameQueue`，再被 render tick 按时钟取走

3. 音视频当前缓冲厚薄不匹配

- 音频 app queue 过厚时，`audio clock` 会明显落后于“已经解码好的媒体时间”
- 视频窗口如果过薄，又还在按 `audioClock + 很小窗口` 保留未来帧
- 就会把后续本该显示的视频连续帧提前裁掉

所以这次真正的问题更准确地说是：

> 不是“读包速度不同”，而是“音频缓冲太厚、视频保留窗口太薄、视频解码又太快”，三者叠加后把 future trim 变成了制造卡顿的源头。

## 12. 当前阶段的最小修正思路

这一轮不推翻 render tick，不重做 ffplay 架构，只做最小修正。

目标不是一下子做到复杂 lip-sync，而是先让下面三件事同时成立：

1. `audio clock` 继续作为主时钟
2. 视频不要再因为 future trim 被提前裁空
3. 音视频两边的缓冲厚薄回到一个更合理的平衡

### 12.1 主同步时钟继续以音频为主

这点不改。

原因：

- 对直播链路来说，最终更稳的主时钟仍然应该是音频
- 音频设备是真实持续消耗数据的一侧
- 只要音频已经稳定播放，视频就更适合“跟随音频”

但要注意：

- “`targetPts == audioClockPts`”不等于“画面已经和音频同步”
- 还必须同时看：
  - `frontVideoPts - audioClockPts`
  - `lastShownVideoPts - audioClockPts`

如果这两个差值很大，即使 `targetPts - audioClockPts = 0`，主观观感上仍然会卡。

### 12.2 future trim 从常规策略降级成异常恢复手段

新的原则是：

- 常规情况下，只丢“明显迟到的旧帧”
- future frame 不作为日常修剪对象
- 只有在队列真的 runaway 时，才允许更温和地裁未来帧

换句话说：

> steady state 靠“背压”控速，异常情况下才靠“future trim”兜底。

这样做的好处是：

- 不会把后续连续显示用的视频帧提前挖空
- render 线程更容易持续拿到“接下来马上要显示的那一小段帧”
- 视频时间轴不会因为过度修剪而出现大洞

### 12.3 音频缓冲变薄，视频窗口只略微变厚

这里不追求“大缓冲保平安”，而是追求“刚刚够用”。

思路是：

- 音频缓冲不要再堆到 2 到 3 秒
- 视频窗口也不要无限放大
- 只是比原来稍微厚一点，保证连续显示有足够的后续帧即可

也就是说：

- 音频缓冲变薄
- 视频窗口略微加厚
- 两边都围绕 `audio clock` 做控制

这比“只放大视频队列”或“只缩音频缓冲”都更稳。

### 12.4 不直接在 decode 线程里写死 sleep，而是做最小背压

如果 decode worker 只是简单写死：

- `sleep(10ms)`
- `sleep(20ms)`

问题是：

- 它依赖猜测，不依赖真实队列状态
- 网络 burst 变化、关键帧大小变化、音频设备消耗节奏变化时，固定 sleep 很容易失效
- 还会引入新的抖动

所以更稳的最小做法是“高低水位背压”：

1. 音频背压

- 当 SDL/PCM queue 太厚时，audio decode worker 暂停继续往前解
- 等 queue 降到低水位再恢复

2. 视频背压

- 当 `VideoFrameQueue` 相对 `audio clock` 已经明显超前时，video decode worker 暂停继续消费新 video tag
- 等 render tick 和音频时钟追上来后再恢复

这样做的核心不是“让线程睡觉”，而是：

> 让 decode 速度服从当前缓冲水位，而不是永远全速往前冲。

## 13. 这一轮实际采用的最小策略

这次代码层面采用的是一套“偏保守、可继续调”的最小参数：

- SDL 音频设备 buffer 从 `2048` 降到 `1024`
- 音频 PCM queue 背压高/低水位先取 `220ms / 120ms`
- live watch 的视频队列实例深度先从原先默认值提升到一个“略厚一点”的范围
- 视频 decode 背压按“相对音频时钟的超前量”和“当前 video queue 深度”共同判断
- future trim 仍然保留，但只作为更宽松的 emergency window，而不是以前那种常态 aggressive trim

这几个数字都不是“最终真理”，只是当前阶段为了先把链路从恶性循环里拉出来的第一版。

后续要继续靠日志收敛，而不是凭感觉拍脑袋调。

## 14. 这轮新增日志重点看什么

为了判断这套思路是不是对的，这次补了几类关键日志。

### 14.1 `trim_detail`

重点看：

- `trigger`
- `cause=too_old/depth_limit/future_window`
- `usingAudioMaster`
- `firstDroppedLeadVsAudioMs`
- `frontPtsBefore/frontPtsAfter`
- `bufferedBeforeMs/bufferedAfterMs`

目标是确认：

- 未来帧是否还在被大量日常裁掉
- 被裁掉的帧相对音频时钟到底超前了多少
- 裁完后是不是把视频连续时间轴切断了

### 14.2 `av_sync`

不要再只看：

- `targetPts - audioClockPts`

更要看：

- `frontVideoPts`
- `frontVsAudioMs`
- `backVideoPts`
- `backVsAudioMs`
- `lastShownVideoPts`
- `lastShownVsAudioMs`

这里的判断重点是：

- 如果 `targetVsAudioMs = 0`，但 `frontVsAudioMs` 还是很大
- 或者 `lastShownVsAudioMs` 长时间停住不动

那就说明：

- 时钟本身没问题
- 真正的问题在“视频可显示帧断档”或者“视频解码/保留策略失衡”

### 14.3 `decode_backpressure`

新增关注：

- `audio_worker decode_backpressure on/off`
- `video worker decode_backpressure on/off`

理想现象不是“永远不开”，也不是“开了就不关”，而是：

- burst 来时短暂打开
- 水位回落后及时关闭
- 系统在一个小范围内来回调节

这说明当前链路开始具备最小的自我稳态能力。

## 15. 这一轮的一句话结论

接入音频以后，直播卡顿的核心已经从“纯视频时钟不稳”变成了：

> 音频主时钟已经建立，但音频缓冲过厚、视频窗口过薄、视频解码过快，再叠加激进 future trim，导致本应后续显示的连续视频帧被提前裁空，render 最后只能长时间停在最后一张已显示画面上等待音频时钟追赶。

所以当前阶段更合理的修正方向是：

- 保持 `audio master`
- 把 future trim 降级成异常恢复手段
- 把音频缓冲压薄
- 把视频窗口只略微加厚
- 用最小背压控制 decode 速度，而不是继续靠提前删 future frame 维持表面同步
