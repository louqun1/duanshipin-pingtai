# 音视频项目亮点：简历两页版

> 这版用于扩展两页简历中的项目经历。写法更接近简历条目，但比一页简历更丰富。整体按“项目概述 / 点播 / 直播 / 用户端 / 服务端部署 / 可压缩亮点”组织。

---

## 1. 项目名称

统一音视频平台原型（点播 + 直播观看 + 主播推流 + WebRTC 连麦）

个人项目 / 核心开发

技术栈可写：

C++17、Qt、FFmpeg、OpenGL、SDL、Media Foundation、WASAPI、Go、MySQL、MinIO、SRS、HLS、RTMP、HTTP-FLV、WebSocket、WebRTC、libdatachannel、coturn、Docker

---

## 2. 项目概述

设计并实现一套面向桌面端的统一音视频平台原型，覆盖短视频点播、直播推流、HTTP-FLV 观看、WebRTC 连麦、服务端混流和用户互动。项目由 Qt/C++ 客户端、Windows 主播端、Go 服务端和虚拟机 Docker 基础设施组成，重点围绕音视频工程核心问题展开，包括媒体转码、播放内核、实时流同步、背压控制、低延迟推拉流、房间信令和 RTC 媒体交互。

项目不是以通用业务 CRUD 为核心，而是围绕完整媒体链路搭建：用户上传视频后进入异步转码和 HLS 分发；主播端采集摄像头和麦克风后编码推 RTMP；观众端通过自研 HTTP-FLV 播放链观看直播；连麦场景通过 WebSocket 信令和 WebRTC 建连，并考虑混流后单路分发给观众。

## 3. 点播模块

### 3.1 媒体上传与异步转码

- 设计点播媒体资产生命周期，覆盖视频上传、原片存储、转码任务创建、后台异步处理、HLS 产物生成、封面生成、状态回写和前端刷新。
- 将上传接口与耗时转码过程解耦，上传成功后快速返回，后台 Worker 专门执行 FFmpeg 转码，避免 HTTP 请求被长时间阻塞。
- 使用 HLS 作为点播播放产物，生成播放清单和切片文件，为对象存储、断点播放、多码率扩展和后续 CDN 分发预留空间。
- 区分原始媒体和可播放媒体产物，原片、HLS 切片、封面图分别进入对象存储，服务端数据库只维护媒体状态和访问地址。
- 为视频引入明确状态流转，覆盖待处理、转码中、可播放、失败等阶段，使前端可以根据服务端状态展示不同 UI，而不是本地猜测。

### 3.2 HLS 点播设计思路

- 选择 H.264 + AAC 作为基础转码输出，兼顾桌面端播放兼容性和后续网页端扩展。
- 通过切片方式把大视频拆成更适合传输和缓存的媒体单元，避免直接暴露原始上传文件作为播放源。
- 点播链路预留多码率扩展空间，后续可以在同一媒体资产下挂载不同清晰度版本。
- 服务端将“上传成功”和“可播放”拆成两个概念，保证用户看到的视频一定经过处理并具备稳定播放入口。

### 3.3 点播状态通知

- 使用 SSE 推送视频状态变化，解决转码任务异步完成后前端无法及时感知的问题。
- 相比轮询，SSE 减少无效请求；相比 WebSocket，SSE 更适合点播状态这种服务端单向通知场景。
- 转码中、转码完成、转码失败等状态可以由服务端主动推送到客户端，首页无需频繁刷新整个列表。
- 前端收到事件后更新对应视频卡片或列表状态，使上传后的用户体验更接近真实媒体平台。

### 3.4 点播互动：点赞

- 设计服务端化点赞链路，将点赞建模为用户与视频之间的关系，而不是前端本地计数。
- 视频列表返回点赞总数和当前用户是否点赞，保证首页展示既有全局统计，也有个性化状态。
- 用户点击点赞或取消点赞后，服务端校验登录态和视频有效性，再写入或删除点赞关系，并返回最新点赞结果。
- 前端根据服务端返回结果更新当前视频卡片，避免重复点赞、未登录点赞、多端状态不一致等问题。
- 该设计可继续扩展到“我的点赞”“用户互动画像”“推荐特征”等后续能力。

### 3.5 点播播放器设计

- 设计播放器控制层，将 UI 命令和底层播放内核隔离，前端只发起打开、播放、暂停、拖动、调音量等高层意图。
- 播放控制层统一维护媒体信息、播放状态、进度、音量和错误状态，避免 UI 与播放内核各自维护状态导致不同步。
- 播放器内部围绕解封装、解码、音视频队列、seek、时钟同步和渲染调度构建，体现对播放器内核机制的理解。
- seek 过程中清理旧队列并重建新的时间轴，避免旧位置缓存帧和新位置解码帧混在一起。
- 播放器事件以高层语义通知 UI，使后续扩展缓冲提示、首帧加载、播放结束推荐、错误重试更加自然。

## 4. 直播模块

### 4.1 直播总体链路

- 将直播拆成主播生产链、观众观看链、连麦互动链三部分，分别解决实时流生产、低延迟播放和多人互动问题。
- 主播端负责采集、预览、编码、封装、RTMP 推流；流媒体服务器负责接收 RTMP 并输出 HTTP-FLV；观众端负责自研拉流、拆包、解码和渲染。
- 连麦场景下，WebRTC 用于主播与上麦端之间的低延迟互动，观众仍然通过单路 HTTP-FLV/RTMP 分发观看最终节目流。
- 设计上区分“互动链路”和“观众分发链路”，避免让所有观众进入 RTC 会话带来的复杂度和扩展压力。

### 4.2 主播端采集与 RTMP 推流

- 基于 Windows 摄像头和麦克风采集能力实现本地音视频输入，并在主播端提供本地预览。
- 采集后的视频编码为 H.264，音频编码为 AAC，再封装为 FLV，通过 RTMP 推流到流媒体服务器。
- 推流前发送媒体元信息、视频初始化信息和音频初始化信息，保证接收端能够正确识别编码参数并初始化解码器。
- 对发布时钟做统一归一化，保证音视频时间戳单调递增，降低接收端因时间戳跳变导致的卡顿和不同步风险。
- 主播端不是依赖现成推流工具，而是掌握从采集、编码、封装到推流的完整媒体生产链路。

### 4.3 主播端实时流水线

- 将采集、视频编码、音频编码、网络发送拆成多个阶段，避免网络发送阻塞采集和编码。
- 阶段之间通过有界队列解耦，防止实时流在网络抖动或编码耗时时无限堆积。
- 当队列超过水位时优先丢弃旧帧，保证实时性和低延迟，而不是为了“不丢帧”导致延迟持续膨胀。
- 记录队列深度、编码耗时、首包延迟、丢帧数量等指标，方便定位推流卡顿、延迟升高和编码瓶颈。
- 同一份采集结果可复用于本地预览、RTMP 推流和 RTC 连麦输入，减少重复打开设备和多路时间轴不一致问题。

### 4.4 HTTP-FLV 直播观看链

- 自研 HTTP-FLV 观看链路，不依赖黑盒播放器直接播放直播 URL。
- 客户端持续读取 HTTP-FLV 字节流，完成 FLV 头校验、音视频标签增量解析、H.264/AAC 解码、音频输出和 OpenGL 视频渲染。
- 直播流按实时字节流处理，支持网络 chunk 与 FLV tag 边界不一致的情况，体现对流式协议的理解。
- 视频解码后进入帧队列，渲染定时器根据目标时钟选择显示、等待或丢弃，而不是解出一帧就立即显示。
- 音频解码为 PCM 后进入音频输出设备，并作为视频同步的重要参考。

### 4.5 直播背压与低延迟控制

- 针对直播 burst 到包、解码速度波动、渲染固定节奏等问题，设计多层背压策略。
- 读流层限制网络读取缓冲，防止上游字节流在客户端无限堆积。
- 音频侧根据音频设备队列和待播放 PCM 时长控制解码速度，避免音频缓冲过厚导致时钟明显滞后。
- 视频侧根据帧队列深度、缓冲时长、视频相对音频时钟的超前量控制解码速度，避免视频提前解码过多造成未来帧堆积。
- 渲染侧丢弃明显迟到的帧，保证直播观看尽量接近当前时间。
- 对未来帧采用更谨慎的保留策略，只在异常情况下裁剪，避免提前丢掉后续即将显示的连续帧。

### 4.6 A/V sync 与音频主时钟

- 接入音频播放后，以音频时钟作为直播播放主时钟，视频围绕音频进度做显示决策。
- 音频连续输出对用户更敏感，因此优先保证音频稳定，再通过视频等待或丢帧实现同步。
- 在日志中观测音频时钟、视频队首时间戳、视频队尾时间戳、最后显示帧和队列缓冲时长，帮助定位卡顿是读流问题、解码问题还是同步策略问题。
- 通过“音频主时钟 + 视频跟随”的方式，使直播观看链路从“能解码”进一步走向“可同步播放”。

### 4.7 WebRTC 连麦与房间信令

- 设计直播房间与连麦业务流程，支持房间成员同步、申请上麦、主播邀请、接受、拒绝、取消和挂断。
- 连麦流程采用状态机管理，明确空闲、等待响应、收到邀请、等待 RTC 参数、RTC 连接中、已连接、结束中等阶段，避免多端异步消息导致状态混乱。
- WebSocket 承载房间成员变化、连麦业务消息和 RTC 建连信令，实现多轮实时交互。
- 连麦接受后再进入 RTC 建连，服务端下发会话参数并绑定业务请求，避免未授权用户绕过业务流程直接建立媒体连接。
- RTC 媒体层采用 H.264 视频和 Opus 音频，完成 PeerConnection 建连、SDP/ICE 交换、音视频轨道收发和远端预览。

### 4.8 混流与观众分发设计

- 连麦后不仅考虑双方能互相看见，还考虑平台观众如何观看最终节目流。
- 互动层使用 WebRTC 解决主播与上麦端低延迟通信，分发层继续使用 RTMP/HTTP-FLV 输出单路节目流。
- 服务端或平台侧可以从多路输入合成一路节目流，视频做布局拼接，音频做重采样和混音，再输出到流媒体服务器。
- 观众端继续只拉一路 HTTP-FLV，不需要感知底层有几路 RTC 或几位上麦用户。
- 这种设计体现了音视频平台中“实时互动”和“大规模分发”分层处理的架构意识。

## 5. 用户端模块

### 5.1 桌面客户端整体设计

- 使用 Qt/C++ 构建桌面客户端，承载短视频浏览、视频上传、点播播放、直播观看、账户登录和点赞交互。
- 客户端采用分层架构，启动装配层创建核心控制对象，主窗口负责导航和页面切换，页面只负责展示和收集输入。
- 业务状态和播放状态由控制层统一维护，页面不直接操作底层播放器、数据库或媒体解码链路。
- 播放器、直播观看、用户体系、上传和点赞都通过明确的交互边界接入，便于后续扩展。

### 5.2 播放器控制与 UI 解耦

- 用户端播放窗口不直接操作底层解码器，而是向统一播放控制层发送播放意图。
- 播放控制层负责维护当前媒体、播放状态、进度、音量、seek 和错误信息。
- 底层播放事件被转换成 UI 可理解的高层事件，降低 UI 对播放器内部实现的依赖。
- 同一套播放控制机制可服务普通窗口和全屏播放，便于复用控制栏、进度条和音量交互。
- 这种设计避免播放按钮、进度条和底层播放器各自维护状态，提高长期可维护性。

### 5.3 首页视频流与点赞体验

- 首页视频卡片展示标题、封面、作者、播放入口、点赞数和当前用户点赞状态。
- 拉取列表时携带用户登录态，使服务端能够返回个性化的“是否已点赞”字段。
- 点赞或取消点赞后，前端只更新当前卡片，减少整页刷新，提高交互流畅度。
- 未登录用户可以浏览和查看点赞数，但不能提交点赞，符合真实平台的权限边界。
- 点赞状态由服务端返回结果驱动，减少本地状态与服务端状态不一致的风险。

### 5.4 上传页与异步状态体验

- 上传页发起视频上传后，用户可以看到视频进入待处理或处理中状态。
- 前端通过服务端事件感知转码完成，自动刷新视频状态和播放入口。
- 上传体验不依赖手动刷新或高频轮询，更接近真实媒体平台的发布体验。
- 当转码失败时，前端可以根据服务端状态展示失败提示，为后续错误详情和重试能力留空间。

### 5.5 直播观看页

- 直播观看页承载 HTTP-FLV 播放入口，用户输入或选择直播地址后进入实时观看链路。
- 页面展示连接状态、播放状态和关键日志，便于联调 RTMP 推流、SRS 分发和客户端拉流解码。
- 直播观看不是普通视频播放控件，而是接入自研的读流、拆包、解码、同步和渲染链路。
- 对直播卡顿、音画不同步、队列积压等问题提供可观察入口，方便学习和排障。

### 5.6 账户与用户身份

- 用户系统支撑登录、注册、会话维护、上传归属、点赞关系、直播房间归属和连麦身份。
- 客户端不把互动行为做成本地假状态，而是围绕服务端用户身份展开。
- 登录态通过请求传递给服务端，使点赞、上传、房间和连麦都能绑定到真实用户。
- 该设计让用户端不只是页面展示，而是平台业务身份和媒体能力的统一入口。

## 6. 服务端与部署模块

### 6.1 Go 服务端能力

- 使用 Go 实现平台服务端，提供用户认证、视频列表、上传、点赞、直播房间、连麦请求、SSE 事件和 WebSocket 信令等能力。
- 服务端负责维护核心业务状态，客户端只展示和提交操作，不在本地伪造关键状态。
- 点播链路中，服务端接收上传并创建转码任务；Worker 完成媒体处理后回写状态并触发事件通知。
- 直播链路中，服务端维护房间、成员和连麦请求状态，并为 RTC 建连提供信令和会话参数。

### 6.2 虚拟机 Docker 基础设施

- 在虚拟机中通过 Docker 部署 MySQL、Redis、MinIO、SRS、coturn，形成接近真实平台的联调环境。
- MySQL 存储用户、会话、视频、点赞、直播房间、成员在线和连麦请求等结构化数据。
- MinIO 存储上传原片、HLS 播放产物和封面图，解耦服务端本地磁盘与媒体资产。
- SRS 接收 RTMP 推流并提供 HTTP-FLV 输出，支撑主播端和观众端完整直播联调。
- coturn 为 WebRTC 提供 STUN/TURN 能力，用于验证 NAT 穿透和 relay-only 场景。

### 6.3 服务端实时能力

- 使用 SSE 承载视频状态和房间状态等服务端单向通知，减少前端轮询。
- 使用 WebSocket 承载房间成员、连麦业务消息和 RTC SDP/ICE 等双向实时信令。
- 将 SSE 和 WebSocket 按场景区分：单向状态通知用 SSE，多轮交互和协商用 WebSocket。
- 连麦消息通过业务请求和会话标识绑定，防止旧会话消息影响新会话，也避免未授权用户直接进入 RTC。

### 6.4 工程化价值

- API、Worker、对象存储、数据库、流媒体服务器分工明确，方便独立排障。
- 通过真实 SRS 和 coturn 联调，项目从本机功能 demo 进一步接近可部署的音视频平台原型。
- 服务端为后续扩展多码率、审核、弹幕、收藏、我的作品、在线状态缓存、多实例广播预留了结构基础。

## 7. 后续扩展规划

> 这一节建议在简历中标注为“后续规划”或“可扩展设计”，不要和已完成能力混写。

### 7.1 多人视频通话

- 规划将现有连麦能力扩展为多人视频通话，业务层继续由自研 Go 服务维护房间、成员、权限、邀请和通话记录。
- 多人音视频转发计划接入成熟 SFU 方案，客户端通过 LiveKit C++ SDK 接入，服务端负责房间创建、token 下发和权限校验。
- 相比客户端 mesh 互连，SFU 转发更适合多人场景，可降低客户端带宽、CPU 和连接复杂度。
- Redis 用于房间在线成员、心跳、麦位、邀请超时等实时热数据，MySQL 用于房间、成员、通话记录和权限数据持久化。

### 7.2 弹幕与评论

- 规划新增弹幕和评论系统，弹幕侧重实时互动，评论侧重长期内容沉淀。
- 弹幕热流、近期弹幕、在线人数、热门计数等高频数据使用 Redis 缓存，提升实时读取和广播效率。
- 评论、弹幕历史、用户行为记录最终写入 MySQL，保证长期查询、审核和数据追溯能力。
- 互动数据继续围绕用户、视频、直播间关系建模，可与已有点赞体系一起扩展为用户互动数据基础。

### 7.3 直播录制与下载

- 规划在主播端增加录制控制能力，由主播端发起开始录制和停止录制请求。
- 后端负责校验主播身份和直播状态，并统一启动录制任务，避免主播端承担额外本地录制压力。
- 录制可基于成熟媒体服务或服务端拉流任务完成，录制完成后保存到服务端或对象存储。
- 后端记录录制状态、文件信息和下载地址，主播端可在录制完成后查看并下载文件。
- 录制产物后续可复用点播链路，扩展为直播回放、自动转码、封面生成和回放管理。

## 8. 可直接放简历的模块化写法

### 点播

- 设计并实现短视频点播媒体管线，打通上传、对象存储、后台异步转码、HLS 切片、封面生成、状态回写和桌面端播放闭环。
- 使用服务端状态机管理视频从上传到可播放的生命周期，区分待处理、转码中、可播放和失败状态，避免前端本地猜测媒体状态。
- 使用 SSE 推送转码完成和视频状态变化，减少轮询并提升上传后的状态反馈及时性。
- 设计服务端化点赞链路，将点赞建模为用户与视频的关系，支持点赞数统计、当前用户点赞状态和后续“我的点赞”等扩展。
- 自研播放器控制层，将 UI 命令、播放器状态和底层播放内核解耦，支撑播放、暂停、seek、进度、音量和错误事件同步。

### 直播

- 实现 Windows 主播端采集、预览、H.264/AAC 编码、FLV 封装和 RTMP 推流，完成从本地设备到 SRS 的实时媒体生产链路。
- 设计采集、音视频编码和网络发送多线程流水线，通过有界队列、旧帧丢弃和水位日志控制实时推流延迟。
- 自研 HTTP-FLV 观看链路，完成实时读流、FLV 标签解析、H.264/AAC 解码、SDL 音频输出和 OpenGL 视频渲染。
- 针对直播卡顿设计多层背压策略，包括网络读缓冲限流、音视频解码高低水位、视频队列深度控制和迟到帧丢弃。
- 接入音频主时钟同步，视频围绕音频播放进度决定等待、显示或丢帧，提升直播观看的音画同步稳定性。
- 设计连麦业务状态机和 WebSocket 信令链路，支持房间成员、申请/邀请、接受/拒绝、取消/挂断和 RTC 建连协商。
- 基于 WebRTC 实现连麦媒体收发，使用 H.264 视频和 Opus 音频完成低延迟互动，并考虑混流后单路分发给观众。

### 用户端

- 使用 Qt/C++ 构建桌面客户端，覆盖首页视频流、上传、点播播放、直播观看、账户登录和点赞交互。
- 采用启动装配、主窗口导航、页面展示、控制层协调的分层架构，降低 UI 与媒体内核、网络服务之间的耦合。
- 首页视频卡片展示点赞数和当前用户点赞状态，用户操作后根据服务端返回结果局部更新卡片。
- 上传页通过服务端事件感知转码完成，自动刷新视频状态和播放入口，提升媒体发布体验。
- 直播页接入自研 HTTP-FLV 播放链，并提供连接状态、播放状态和关键日志展示，便于定位拉流、解码和同步问题。
- 用户身份贯穿上传归属、点赞关系、直播房间和连麦请求，为后续个人主页、我的作品、我的点赞等功能扩展打基础。

### 服务端与部署

- 使用 Go 实现平台服务端，提供用户、视频、上传、点赞、直播房间、连麦请求、SSE 事件和 WebSocket 信令等能力。
- 将 API 与 Worker 解耦，API 负责业务入口和状态管理，Worker 负责耗时媒体转码，提高系统可扩展性和可排障性。
- 在虚拟机 Docker 环境部署 MySQL、MinIO、SRS、coturn 等服务，支撑真实的存储、推流、拉流和 RTC 穿透联调。
- 使用 MinIO 管理原片、HLS 产物和封面图，使用 SRS 承载 RTMP ingest 与 HTTP-FLV watch，使用 coturn 支撑 WebRTC 网络穿透。
- 区分 SSE 与 WebSocket 的使用场景，单向状态通知走 SSE，多轮实时协商和连麦信令走 WebSocket。

### 后续规划

- 规划接入 LiveKit C++ SDK 和 SFU 服务扩展多人视频通话，由自研服务端维护房间、权限、token 和通话记录。
- 规划新增弹幕与评论系统，Redis 承载实时热数据，MySQL 负责历史数据和业务关系持久化。
- 规划增加直播录制能力，主播端发起录制，后端启动录制任务并保存文件，录制完成后主播端可下载。
