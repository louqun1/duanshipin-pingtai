# 点播点赞接入

## 1. 这一步做了什么

在“用户系统服务端化”和“上传归属打通”之后，当前已经继续完成了点赞链路。

这一步让用户和视频之间不再只有“谁上传了它”这一层关系，还新增了“谁点赞了它”这一层互动关系。

## 2. 整体思路

整体仍然遵循同一条主线：

1. 用户身份以服务端 MySQL 为准
2. 点赞数据存到服务端
3. 前端只通过 API 读取和提交点赞状态
4. 首页卡片直接展示点赞数和当前用户是否已点赞

也就是说，点赞没有做在客户端本地，而是继续建立在服务端用户体系上。

## 3. 当前接口

### 3.1 点赞接口

- `POST /api/videos/{id}/like`
  当前登录用户给指定视频点赞

- `DELETE /api/videos/{id}/like`
  当前登录用户取消点赞

这两个接口都要求携带：

```http
Authorization: Bearer <token>
```

### 3.2 视频读取接口

点赞接入之后，以下接口现在除了视频基础信息，还会返回点赞相关字段：

- `GET /api/videos`
- `GET /api/videos/{id}`

新增返回字段：

- `likeCount`
  当前视频的点赞总数

- `likedByMe`
  当前登录用户是否已经点赞过该视频

## 4. 当前数据结构

服务端新增了点赞表：

```sql
video_likes
- video_id
- user_id
- created_at
```

这张表表达的是：

- 哪个用户点赞了哪个视频
- 一个用户是否已经点赞过某个视频
- 某个视频累计有多少点赞

其中 `(video_id, user_id)` 是天然唯一的一组关系，因此同一个用户不会重复点赞同一个视频。

## 5. 前端现在怎么工作

首页卡片现在已经支持点赞展示和提交：

- 卡片会显示 `Like N` 或 `Liked N`
- 点击后会直接调用服务端点赞接口
- 成功后当前卡片立即更新，不需要再轮询整个列表
- 未登录时仍然能看到点赞数，但不能真正提交点赞

同时，首页读取视频列表时会带上当前登录用户的 Bearer Token，这样服务端才能返回准确的 `likedByMe`。

## 6. 这一步的意义

这一步验证了两件关键事情：

1. 服务端用户体系已经能承载互动数据，而不只是登录和上传归属
2. 视频相关行为已经开始围绕 `user_id + video_id` 这组核心关系展开

这对后续能力很重要，因为下面这些功能都可以沿着同一套路继续扩展：

- 弹幕
- 收藏
- 我的点赞
- 我的作品

## 7. 下一步建议

如果继续按主线往下推进，最自然的下一步有两个方向：

1. 接入 `video_danmaku`
   先把“哪个用户在什么时间点发了什么弹幕”打通

2. 做“我的视频 / 我的点赞”
   让用户页真正开始承载点播数据

如果只选一个 next step，优先推荐弹幕表和弹幕接口设计。
