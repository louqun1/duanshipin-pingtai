# 服务器构建

## 1. 这份文档解决什么

这份文档专门回答一个问题：

- 你现在不在学校，不能继续依赖原来的校内局域网服务器。
- 你手里只有本机虚拟机，IP 是 `192.168.99.128`。
- 你想知道当前仓库里的 server 应该怎么搭，哪些服务必须起，哪些可以先不配。

先说结论：

- 现在这套仓库完全可以先跑在你自己的虚拟机上。
- 你可以先不配 `coturn`。
- 不配 `coturn` 不影响点播。
- 不配 `coturn` 不影响 `RTMP ingest -> HTTP-FLV watch` 这条直播观看链路。
- 不配 `coturn` 会影响 WebRTC 连麦在复杂 NAT / 跨网络环境下的成功率。

所以，当前最推荐的顺序不是“先把所有服务一次性堆满”，而是：

1. 先把点播服务端跑通。
2. 再把 SRS 跑起来，打通 RTMP 推流和 HTTP-FLV 观看。
3. 最后在你真的开始做 WebRTC 连麦联调时，再补 `coturn`。

这更符合你现在的学习优先级。

## 2. 先理解当前服务端组成

当前仓库里的服务端不是一个单独进程，而是几块东西拼起来的：

- `server/cmd/api`：Go API，负责 HTTP 接口、`/ws` 信令、`/vod` 和 `/image` 代理读取。
- `server/cmd/worker`：Go Worker，负责轮询转码任务，用 `ffprobe` / `ffmpeg` 生成 HLS 和封面。
- `MySQL`：存用户、视频、直播间、转码任务等业务数据。
- `MinIO`：存原始上传文件、HLS 产物、封面图。
- `SRS`：负责直播侧 `RTMP ingest -> HTTP-FLV output`。
- `coturn`：只在 WebRTC 连麦、尤其是跨 NAT / 复杂网络时才重要。

可以把数据流先看成三条主链路。

### 2.1 点播链路

```text
Qt 客户端
  -> Go API :8080
  -> MySQL 记录视频元数据
  -> MinIO 保存原始文件
  -> Worker 拉取转码任务
  -> ffmpeg 生成 HLS + cover
  -> MinIO 保存 HLS 和封面
  -> Go API 对外返回 /vod/... 和 /image/...
```

### 2.2 直播观看链路

```text
OBS / ffmpeg 推流
  -> SRS RTMP :1935
  -> SRS 输出 HTTP-FLV :18080
  -> Qt 客户端 / ffplay 拉流观看
```

### 2.3 WebRTC 连麦链路

```text
客户端
  -> Go API /ws + /api/live-rooms
  -> 信令交换 offer / answer / ice candidate
  -> 浏览器 / probe / 客户端直连或经 TURN 中继
```

你现在没有 `coturn` 时，前两条链路都能正常学、正常跑。第三条链路可以先做信令流转和同网段实验，但不要把“跨网连不起来”第一时间判成业务代码错误。

## 3. 当前环境下的推荐搭建方案

你的当前场景最适合下面这套方式：

- Windows 主机跑 Qt 客户端。
- Ubuntu 虚拟机跑 Go API、Go Worker。
- Ubuntu 虚拟机里的 Docker 跑 `mysql`、`redis`、`minio`、`srs`。
- 先不启动 `coturn`。

为什么这样拆：

- 这和仓库当前真实结构一致，改动最少。
- 点播链路最依赖 `API + Worker + MySQL + MinIO`。
- HTTP-FLV 观看最依赖 `SRS`。
- `coturn` 只在 WebRTC 进入实战联调时再补最划算。

## 4. 开始前先确认两件事

### 4.1 先确认 Windows 能访问虚拟机

在 Windows 宿主机上先确认：

```powershell
ping 192.168.99.128
```

如果这里都不通，先不要急着折腾服务端代码，先把虚拟机网络打通。

至少要保证 Windows 宿主机可以访问这台虚拟机的 `192.168.99.128`。

### 4.2 先确认虚拟机里有这些基础工具

在 Ubuntu 虚拟机里：

```bash
docker --version
docker compose version
go version
ffmpeg -version
ffprobe -version
```

如果缺工具，先补：

```bash
sudo apt update
sudo apt install -y git curl ffmpeg golang-go
```

## 5. 先启动基础设施容器

在仓库根目录执行：

```bash
cd ~/duanshipin-pingtai
docker compose up -d mysql redis minio srs
docker compose ps
```

说明：

- 这里故意没有带 `coturn`。
- `redis` 当前最小链路不是强依赖，但一起起掉也没问题。
- Go API 和 Worker 不是 Compose 里的容器，它们要在虚拟机系统里单独跑。

当前 Compose 暴露的关键端口是：

- MySQL：`3307`
- Redis：`6380`
- MinIO API：`9000`
- MinIO Console：`9001`
- SRS RTMP：`1935`
- SRS HTTP API：`1985`
- SRS HTTP-FLV：`18080`

这里有一个很重要的点：

- 你现在本机虚拟机场景下，HTTP-FLV 更应该访问 `18080`。
- 旧文档里如果写成 `http://192.168.99.128:8080/live/...`，那是旧环境/旧映射思路，不要直接照抄。

也就是说，当前更推荐的直播观看地址是：

```text
http://192.168.99.128:18080/live/room1.flv
```

如果虚拟机开了防火墙，再放行这些端口：

```bash
sudo ufw allow 8080/tcp
sudo ufw allow 1935/tcp
sudo ufw allow 18080/tcp
sudo ufw allow 9000/tcp
sudo ufw allow 9001/tcp
```

## 6. 配置 Go API / Worker 环境变量

进入 `server/` 目录前，先把环境变量显式导出来：

```bash
export HTTP_ADDR=:8080
export PUBLIC_BASE_URL=http://192.168.99.128:8080       ##这个是必须的
export PUBLIC_SIGNALING_URL=ws://192.168.99.128:8080/ws

export MYSQL_DSN='vod_user:vod_pass_123@tcp(127.0.0.1:3307)/vod_platform?charset=utf8mb4&parseTime=True&loc=Local'

export MINIO_ENDPOINT=127.0.0.1:9000
export MINIO_ACCESS_KEY=minioadmin
export MINIO_SECRET_KEY=minioadmin123
export MINIO_USE_SSL=false
export MINIO_RAW_BUCKET=raw-media
export MINIO_VOD_BUCKET=vod-media
export MINIO_IMAGE_BUCKET=image-assets
```

这里一定不要偷懒依赖默认值。

原因是当前代码里的默认回退地址还是旧的 `192.168.3.28` 思路，所以你现在这台虚拟机必须明确写：

- `PUBLIC_BASE_URL=http://192.168.99.128:8080`
- `PUBLIC_SIGNALING_URL=ws://192.168.99.128:8080/ws`

如果你想长期生效，可以写进 `~/.bashrc`。

## 7. 编译并启动 Go 服务

先拉依赖、编译：

```bash
cd ~/duanshipin-pingtai/server
go mod tidy

mkdir -p build
go build -o build/api ./cmd/api
go build -o build/worker ./cmd/worker
go build -o build/importer ./cmd/importer
```

说明：

- `api` 是必须的。
- `worker` 对“上传后自动转码出 HLS”是必须的。
- `importer` 不是当前最小启动前置条件。

先开 API：

```bash
cd ~/duanshipin-pingtai/server
./build/api
```

再开 Worker：

```bash
cd ~/duanshipin-pingtai/server
./build/worker
```

如果你只是临时调试，也可以直接：

```bash
go run ./cmd/api
go run ./cmd/worker
```

## 8. 现在先不配 coturn，会影响什么

### 8.1 不受影响的部分

- 用户注册/登录
- 点播上传
- Worker 转码
- HLS 播放
- RTMP 推流
- HTTP-FLV 观看
- `/ws` 和 `/api/live-rooms/*` 这类信令/业务接口本身

### 8.2 会受影响的部分

- WebRTC 在复杂 NAT 下的稳定建链
- 两端不在同一网段时的 ICE 候选可达性
- 强依赖 relay candidate 的连麦联调

### 8.3 你现在应该怎么理解这件事

如果你现在的目标是：

- 学点播服务端闭环
- 学 `RTMP ingest -> HTTP-FLV watch`
- 先把信令流走通

那你完全可以先不配 `coturn`。

如果你下一阶段开始做：

- 跨网络 WebRTC
- 多人连麦稳定性
- `--relay-only` 探针验证

再补 `coturn` 最合适。

## 9. 如何验证当前搭建成功

建议按下面顺序验证。

### 9.1 先验 API

```bash
curl http://127.0.0.1:8080/healthz
```

期望返回：

```json
{"status":"ok"}
```

再查视频列表：

```bash
curl http://127.0.0.1:8080/api/videos
```

### 9.2 再验点播播放地址逻辑

如果后面你已经有视频数据了，再查单条视频或列表，重点看：

- `playUrl` 应该指向 `http://192.168.99.128:8080/vod/...`
- `coverUrl` 应该指向 `http://192.168.99.128:8080/image/...`

而不是直接指向 MinIO 的 `:9000`。

### 9.3 再验直播推流和 HTTP-FLV

先向 SRS 推流：

```bash
ffmpeg -re -i /path/to/demo.mp4 -c:v libx264 -c:a aac -f flv rtmp://192.168.99.128/live/room1
```

然后在另一终端或 Windows 宿主机上拉流验证：

```bash
ffplay http://192.168.99.128:18080/live/room1.flv
```

如果你能看到画面，说明这条链路已经通了：

```text
ffmpeg / OBS
  -> RTMP 1935
  -> SRS
  -> HTTP-FLV 18080
  -> 播放端
```

### 9.4 最后再验客户端

客户端联调时，优先检查：

- API 地址是不是 `http://192.168.99.128:8080`
- HLS 地址是不是 `http://192.168.99.128:8080/vod/...`
- HTTP-FLV 地址是不是 `http://192.168.99.128:18080/live/...`

## 10. 如果以后要补 coturn，应该怎么做

等你真的开始做 WebRTC 连麦时，再补下面这几步。

### 10.1 改对配置文件

Compose 实际挂载的是：

- `ops/coturn/turnserver.conf`

不是仓库根目录那个 `turnserver.conf`。

你至少要把里面和旧 IP 相关的地方改成：

```text
relay-ip=192.168.99.128
external-ip=192.168.99.128
```

### 10.2 再启动 coturn

```bash
cd ~/duanshipin-pingtai
docker compose up -d coturn
docker compose ps coturn
docker compose logs --tail=50 coturn
```

### 10.3 再放行端口

```bash
sudo ufw allow 3478/tcp
sudo ufw allow 3478/udp
sudo ufw allow 49160:49200/udp
```

### 10.4 再用新的虚拟机地址联调

后续如果你要跑 probe，ICE 地址应该换成：

```text
turn://probe:probe_turn_123@192.168.99.128:3478?transport=udp
```

## 11. 你现在最推荐的落地顺序

如果站在“先学核心链路、再补复杂网络”的角度，我建议你现在就按这条路线走：

1. 起 `mysql + redis + minio + srs`，先不管 `coturn`。
2. 起 `api + worker`。
3. 先验证 `/healthz`、`/api/videos`。
4. 先把上传、转码、HLS 播放跑通。
5. 再用 `ffmpeg -> SRS -> HTTP-FLV` 跑直播观看。
6. 最后等你需要做 WebRTC 连麦稳定性，再补 `coturn`。

这是你当前环境下最省力、也最符合音视频学习主线的搭建方式。
