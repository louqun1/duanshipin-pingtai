# 音视频项目亮点：面试讲解版

> 这版用于面试前复盘和现场讲项目。重点不是罗列实现细节，而是把项目讲成一个完整的音视频平台工程：为什么这么设计、链路如何流转、解决了哪些真实问题、面试官可以往哪里深挖。

---

## 1. 一句话介绍项目

我做的是一个面向桌面端和服务端的统一音视频平台原型，覆盖短视频点播、直播推流、HTTP-FLV 观看、WebRTC 连麦和服务端混流分发。

项目不是单纯做几个页面，而是围绕音视频工程核心能力搭建：上传转码、HLS 点播、RTMP 推流、HTTP-FLV 拉流解码、播放器状态机、A/V sync、背压与丢帧、WebSocket 信令、RTC 建连、虚拟机 Docker 部署。

---

## 2. 项目整体怎么讲

面试时可以先按“三端一服务”来讲：

- 服务端：负责用户、视频、点赞、直播房间、连麦请求、转码任务、状态通知和信令转发。
- 用户端：负责短视频浏览、上传、播放、直播观看、点赞、登录态交互。
- 主播端：负责摄像头/麦克风采集、本地预览、编码、RTMP 推流和 WebRTC 连麦媒体。
- 基础设施：MySQL、MinIO、SRS、coturn 等跑在虚拟机 Docker 环境里，支撑存储、转码、推流、拉流和 RTC 穿透。

然后强调项目的主线：

> 点播解决“视频资产怎么生产和播放”，直播解决“实时媒体怎么生产和观看”，连麦解决“多人实时互动怎么接入平台”，用户端解决“这些媒体能力怎么变成可操作的产品体验”。

---

## 3. 点播怎么讲

### 3.1 点播整体链路

点播不是上传一个文件后直接播放，而是一条媒体资产生产管线。

可以这样讲：

用户在客户端上传视频后，服务端把原片存到对象存储，同时创建转码任务。后台 Worker 异步调用 FFmpeg，把原片转成 HLS，包括播放清单、切片和封面。转码完成后，服务端更新视频状态，并通过 SSE 通知前端刷新。前端看到视频从“处理中”变成“可播放”，再进入播放器播放。

这条链路体现的是：

- 上传接口和转码任务解耦。
- 原片和播放产物分离。
- 视频状态由服务端驱动。
- 前端不靠轮询猜状态，而是接收服务端事件。

### 3.2 为什么这么设计

如果上传接口直接做转码，请求会很慢，也容易失败；如果前端只本地保存状态，刷新页面后状态就丢了。所以我把“上传”和“转码”拆开，让服务端记录媒体资产状态，Worker 专门处理耗时任务。

选择 HLS 是因为它更接近真实点播平台的分发模型。HLS 把视频拆成清单和切片，适合对象存储、缓存、后续 CDN、多码率扩展和断点播放。

### 3.3 面试可展开点

面试官如果问点播，可以展开：

- 上传完成为什么不等于可播放。
- 为什么需要转码任务队列。
- HLS 切片相比直接播放原文件有什么好处。
- 转码失败如何反馈给前端。
- SSE 为什么适合通知转码完成。
- 对象存储为什么适合放媒体产物。

如果面试官继续追问代码落点，可以提这些锚点：

- 转码 Worker 完成处理后，通过 `notifyVideoUpdated` 通知 API。
- API 侧通过 `handleVideoUpdatedNotification` 接收内部事件，再由 `publishVideoUpdated` 推送 `video.updated`。
- SSE 长连接由 `handleEvents` 管理，底层用 `eventBroker.publish` 统一广播事件。
- 点播列表返回时会带上 `likeCount` 和 `likedByMe`，这样前端不用二次请求点赞状态。

### 3.4 点播互动：点赞怎么讲

点赞不是前端本地计数，而是服务端用户行为。

讲法：

首页拉取视频列表时，服务端会根据当前登录用户返回每个视频的点赞数，以及“我是否已经点赞”。用户点击点赞或取消点赞后，前端带登录态请求服务端，服务端校验用户和视频，再写入或删除用户与视频之间的点赞关系，最后返回最新点赞数和当前状态，前端只更新当前卡片。

这个设计的重点是：

- 点赞是用户和视频之间的关系。
- 不能只存一个数字，否则无法知道谁点过赞。
- 服务端返回最终状态，避免重复点赞和多端状态不一致。
- 后续可以自然扩展“我的点赞”“互动推荐”“用户画像”。

源码追问时可以落到：

- `handleVideoLike`：统一处理点赞和取消点赞入口。
- `addVideoLike`：写入用户和视频的点赞关系，并用唯一关系避免重复点赞。
- `removeVideoLike`：取消点赞。
- `findVideoLikeState`：返回最新点赞数和当前用户是否已点赞。
- `video_likes`：表达 `user_id + video_id` 的互动关系。

### 3.5 播放器控制链怎么讲

点播播放器可以强调“UI 命令、控制器状态、播放内核”三层。

可以这样讲：

前端播放窗口不直接操作 FFmpeg，而是把打开视频、播放、暂停、seek、调音量这些动作交给播放器控制器。控制器维护当前媒体和播放状态，再调用底层播放器。底层播放器产生 prepared、progress、seek complete、playback finished、error 这类消息后，控制器再翻译成 UI 能消费的事件。

源码追问时可以落到：

- `AppBootstrap`：程序启动时创建 `PlayerController`，再注入主窗口。
- `PlayerController::openMedia`：前端打开视频的统一入口。
- `PlayerController::requestTogglePlayback`：播放/暂停切换入口。
- `PlayerController::requestSeek`：进度条拖动后的 seek 入口。
- `PlayerController::handlePlayerEvent`：把底层播放器事件翻译成上层 UI 状态。
- `IjkMediaPlayer::seekTo`：播放器状态层处理 seek 前后状态。
- `FFPlayer::ffp_seek_to_l` / `stream_seek`：底层真正发起 seek 请求。

这里可以重点讲一句：

> seek 不是改一个进度变量，而是要让旧 packet/frame queue 失效，重建新的时间轴，否则新旧位置的包和帧会混在一起。

## 4. 直播怎么讲

### 4.1 直播分三条链

直播模块建议按三条链路讲：

- 主播生产链：采集、编码、封装、RTMP 推流。
- 观众观看链：HTTP-FLV 拉流、拆包、解码、音频输出、视频渲染。
- 连麦互动链：房间状态、WebSocket 信令、RTC 媒体收发、混流分发。

这能让面试官听到你不是只会“推流成功”，而是理解直播平台从生产到分发再到互动的完整结构。

### 4.2 主播端推流链怎么讲

主播端在 Windows 上采集摄像头和麦克风，本地预览同时把音视频送入编码链路。视频编码成 H.264，音频编码成 AAC，再封装成 FLV，通过 RTMP 推到 SRS。SRS 接收推流后，观众端可以通过 HTTP-FLV 拉取观看。

亮点是：

- 不是依赖 OBS 或黑盒 SDK，而是自己组织采集、编码、封装、发送。
- 采集、编码、发送分阶段解耦。
- 推流前发送元信息和音视频初始化信息，接收端才能正确识别码流。
- 发布时钟做归一化，避免不同采集源时间戳跳变导致接收端卡顿。

### 4.3 主播端为什么要做多线程流水线

实时推流里，采集、编码、网络发送的速度不可能永远一致。如果都放在一个循环里，网络慢会卡住编码，编码慢会卡住采集，最终表现为预览卡、推流卡、延迟越来越大。

所以设计上把它拆成：

- 采集阶段：稳定拿到原始音视频。
- 视频编码阶段：单独处理视频。
- 音频编码阶段：单独处理音频。
- 发送阶段：单独处理 RTMP 发送。

阶段之间通过有界队列连接。队列满时优先丢旧帧，控制延迟和内存，而不是无限堆积。

面试时可以强调：

> 直播系统里，“永远不丢帧”不一定是好事。如果为了不丢帧导致延迟越来越高，用户看到的是过去的画面。实时系统更重要的是延迟可控和链路稳定。

### 4.4 观众端 HTTP-FLV 观看链怎么讲

观众端没有把 HTTP-FLV 地址直接交给系统播放器，而是自己做了观看链路。

可以这样讲：

客户端从 HTTP-FLV 地址持续读取字节流，先校验 FLV 头，再增量解析出音频、视频和脚本标签。视频标签进入 H.264 解码，音频标签进入 AAC 解码。音频解码成 PCM 后送到音频设备播放，视频解码成帧后进入视频队列，由渲染定时器根据时钟决定显示哪一帧，最后通过 OpenGL 渲染。

这条链路体现：

- 理解 HTTP-FLV 是实时字节流，不是普通文件。
- 理解 FLV tag、sequence header、H.264、AAC 的关系。
- 理解音视频解码和渲染不能简单“收到就画”。
- 理解实时流里必须做缓冲、同步、丢帧和背压。

源码追问时可以落到：

- `HttpFlvStreamReader::open`：发起 HTTP-FLV GET。
- `HttpFlvStreamReader::handleReadyRead`：持续读取网络 chunk。
- `FlvDemuxer::pushBytes`：增量喂入字节并解析 FLV tag。
- `FlvDemuxer::parseFlvHeader`：校验 FLV header。
- `FlvVideoDecoder::pushTag`：处理 AVC/H.264 视频 tag。
- `FlvAudioDecoder::pushTag`：处理 AAC 音频 tag。
- `VideoFrameQueue`：缓存解码后的视频帧，供 render tick 消费。
- `onRenderTick`：按时钟驱动显示，而不是解出就画。

### 4.5 直播卡顿和背压怎么讲

这是项目最适合深挖的亮点。

可以用这个逻辑讲：

直播卡顿不一定是没收到流，也不一定是解码失败。很多时候是上游突然来了一批数据，解码很快把帧推到队列里，但渲染是按时钟消费的，队列就可能堆积到未来。此时如果处理不好，屏幕会停在上一帧，看起来像卡住。

所以我做了多层背压：

- 网络读流层：下游处理不过来时限制读缓冲，避免字节流无限灌入。
- 解码层：根据音频缓冲、视频队列深度、视频相对音频时钟的超前量控制是否继续解码。
- 队列层：迟到帧可以丢，未来帧谨慎裁剪，防止把后续连续画面提前删空。
- 渲染层：视频不盲目显示，而是围绕目标时间戳决定等待、显示或丢弃。

一句话总结：

> 背压的核心是让上游服从下游消费能力；丢帧的核心是保证直播的当前性，而不是把历史画面慢慢补完。

源码追问时可以落到：

- `HttpFlvStreamReader::setReadThrottled`：通过限制读取缓冲做入口背压。
- `LivePlayerSession::updateDecodeBackpressure`：统一判断音频、视频和入口背压是否开启。
- `LiveVideoDecodeWorker::setDecodeBackpressure`：视频解码 worker 按水位暂停/恢复。
- `LiveAudioDecodeWorker::setDecodeBackpressure`：音频解码 worker 按 PCM backlog 暂停/恢复。
- `dropLateQueuedVideoFrames`：丢弃明显迟到的视频帧。
- `trimQueuedVideoFramesForPlaybackWindow`：控制播放窗口，避免队列无限堆积。
- `maybeReanchorPlaybackClock`：纯视频阶段处理队列整体跑到未来时的时钟重锚定。

### 4.6 音频主时钟怎么讲

接入音频后，我让视频跟随音频时钟。

原因是：

- 人耳对音频卡顿更敏感。
- 音频设备是持续消费的一侧。
- 视频可以通过等待或丢帧来对齐音频。

可以这样讲：

> 视频不是解出来就立刻显示，而是看当前音频播放到哪里，再决定这帧是该等、该播还是该丢。这样直播观看更接近真实播放器的 A/V sync 思路。

源码追问时可以落到：

- `currentTargetVideoPtsMs`：计算当前应该显示到哪个视频 PTS。
- `SdlAudioOutput`：提供音频播放时钟和音频队列快照。
- `onRenderTick`：周期性读取音频时钟，决定视频显示节奏。
- `av_sync` 日志：观察音频时钟、视频队首/队尾、最后显示帧之间的差值。

### 4.7 连麦怎么讲

连麦不是一个按钮，而是业务状态、实时信令和 RTC 媒体三层组合。

业务层负责：

- 谁在房间里。
- 谁发起申请。
- 谁邀请谁。
- 谁接受、拒绝、取消、挂断。
- 当前是否已有活跃连麦。

信令层负责：

- 通过 WebSocket 同步房间成员和连麦状态。
- 连麦接受后交换 RTC 建连参数。
- 转发 SDP 和 ICE。
- 用请求标识和会话标识把业务请求与 RTC 会话绑定。

媒体层负责：

- 建立 WebRTC 连接。
- 发送和接收音视频轨道。
- 主播端复用已有采集结果，避免重复打开摄像头和麦克风。

可以总结：

> 我不是让任何连上 WebSocket 的人都能直接发 RTC offer，而是先走业务授权和状态机，确认连麦被接受后，再进入 RTC 建连。这样业务和媒体边界更清楚，也更接近真实平台。

源码追问时可以落到：

- 服务端 `linkmic_requests`：记录一条连麦请求的业务状态。
- 服务端 `publishLiveRoomEvent`：房间或连麦状态变化后发布房间事件。
- `BusinessLiveClient`：主播端业务 WebSocket 客户端，承载房间和连麦消息。
- `LinkMicSession`：客户端连麦业务状态机，处理 invite、accept、reject、cancel、hangup。
- `LinkMicRoomState`：维护本地连麦阶段，例如等待响应、等待 join 参数、RTC 连接中、已连接。
- `RtcSignalingBridge`：把业务 WebSocket 消息和 RTC SDP/ICE 消息隔离开。
- `RtcPeerSession`：真正创建 PeerConnection，管理音视频 track。
- `setMediaTapCallbacks`：把已有采集结果旁路给 RTC，避免重复开设备。

### 4.8 为什么要把 RTC 互动和观众分发分开

RTC 适合少数人低延迟互动，但不适合所有观众都进入同一个 RTC 会话。观众侧更适合拉一路稳定的 HTTP-FLV 或 HLS。

所以设计上：

- 主播和嘉宾之间走 RTC，解决低延迟互动。
- 平台输出一路节目流，解决观众观看。
- 连麦后可以做混流，把多路画面和音频合成一路。
- 观众端仍然只看一路流，不需要理解多路 RTC。

这体现的是音视频平台架构意识，而不是只做点对点 demo。

## 5. 用户端怎么讲

### 5.1 用户端不是简单页面，而是媒体能力入口

用户端承担的是把服务端和播放器能力变成产品体验：

- 首页展示点播视频。
- 上传页发起媒体资产生产流程。
- 播放窗口接入自研播放器控制链。
- 直播页接入 HTTP-FLV 观看链。
- 账户页维护登录态。
- 点赞、上传、播放、直播观看都围绕服务端状态工作。

### 5.2 客户端架构怎么讲

客户端按分层设计：

- 启动装配层创建全局控制器。
- 主窗口只负责导航和页面切换。
- 页面只负责展示和收集输入。
- 控制器负责接收命令、维护状态、通知页面。
- 媒体能力放在独立播放和直播观看链路里。

可以这样讲：

> 我没有让页面直接操作播放器底层或数据库，而是通过控制器接住 UI 命令，再把底层消息翻译成 UI 能理解的事件。这样页面不会被 FFmpeg、网络、播放器状态污染。

源码追问时可以落到：

- `AppBootstrap`：启动装配层，统一创建播放控制器和直播控制器。
- `MainWindow`：只负责页面容器和导航。
- `VideoPlayerWindow`：只负责播放 UI 和用户交互。
- `PlayerController`：承接播放命令并输出播放事件。
- `LivePlayerController`：承接直播观看命令并输出直播播放状态。

### 5.3 播放器控制器怎么讲

为了让播放器可维护，我做了命令流和事件流的分离。

用户点击按钮时，UI 只表达意图，比如打开、播放、暂停、拖动、调音量。控制器负责把这些意图转给底层播放器，并维护统一播放状态。底层播放器产生准备完成、进度变化、seek 完成、播放结束、错误等事件，再由控制器翻译后通知 UI。

好处是：

- UI 不直接依赖底层播放器消息。
- 播放状态有唯一来源。
- 后续加首帧加载、缓冲提示、错误重试、全屏控制更容易。
- 播放窗口关闭或切换页面时，生命周期更清晰。

### 5.4 前后端状态机怎么讲

项目里多个地方都用了状态机思想：

- 点播：上传、转码中、可播放、失败。
- 播放器：空闲、打开中、准备好、播放中、暂停、seek 中、完成、错误。
- 直播观看：连接中、读流中、解码中、播放中、错误。
- 连麦：空闲、等待响应、收到邀请、等待 RTC 参数、RTC 连接中、已连接、结束中。

状态机的价值是：

- 每个阶段能做什么很明确。
- 非法操作可以拒绝。
- 异步事件来了不会乱改 UI。
- 日志和排障更容易。

面试中可以说：

> 我把复杂异步流程都尽量变成“当前状态 + 事件 -> 新状态 + 副作用”。这对播放器、转码和连麦都很重要。

### 5.5 SSE 和 WebSocket 的分工

项目里没有所有实时能力都用 WebSocket，而是区分场景。

SSE 用于：

- 视频转码完成。
- 视频状态更新。
- 直播房间状态变更。

WebSocket 用于：

- 房间成员在线同步。
- 连麦申请和邀请。
- RTC 建连信令。

可以这样讲：

> SSE 适合服务端单向通知，WebSocket 适合双向、多轮、强实时交互。点播转码状态用 SSE 更轻，连麦信令用 WebSocket 更合适。

## 6. 服务端和部署怎么讲

### 6.1 虚拟机 Docker 部署

项目服务端不是纯本机内存 demo，而是在虚拟机里部署真实依赖：

- MySQL 存用户、视频、点赞、房间和连麦请求。
- MinIO 存原片、HLS 切片、封面。
- SRS 接收 RTMP 并提供 HTTP-FLV。
- coturn 支撑 WebRTC 的 STUN/TURN。
- Redis 预留给在线状态、缓存、多实例同步等。

面试中可以说：

> 这套部署让我能在本地 Windows 客户端、主播端和虚拟机服务端之间完成真实联调，而不是所有东西都在一个进程里模拟。

### 6.2 服务端职责划分

服务端可以按四块讲：

- 业务 API：用户、视频、点赞、房间、连麦请求。
- 媒体任务：上传、转码、HLS 产物、封面。
- 实时通知：SSE 推送状态变化。
- 信令服务：WebSocket 转发房间消息和 RTC 建连消息。

这说明服务端不是只有 CRUD，而是承载了音视频平台的媒体状态流转和实时协作。

源码追问时可以落到：

- `handleEvents`：SSE 客户端订阅入口。
- `eventBroker`：服务端内存事件广播器。
- `handleVideoLike`：点赞互动入口。
- `handleVideoUpdatedNotification`：Worker 通知 API 推送视频更新。
- 直播房间接口：负责创建房间、成员在线、申请/邀请/接受/挂断。
- WebSocket 信令入口：负责 room、linkmic、rtc 三类消息的实时转发。

## 7. 后续扩展规划怎么讲

这一部分面试时要说清楚是“后续规划”，不要和已完成能力混在一起。可以作为项目的可扩展性来讲。

### 7.1 多人视频通话规划

当前连麦更偏向“小规模上麦”和平台直播场景，后续如果要做真正的多人视频通话，我会优先考虑引入成熟的 SFU 服务，而不是继续自己写多人媒体转发。

规划思路是：

- 客户端继续保留 Qt/C++ 主体。
- RTC 能力接入成熟的 LiveKit C++ SDK。
- 服务端负责创建房间、生成 token、维护用户和房间权限。
- 多人音视频不再由客户端之间互相 mesh 连接，而是由 LiveKit 服务端进行转发。
- MySQL 持久化会议房间、成员、通话记录、权限和回放记录。
- Redis 存储房间在线成员、临时麦位状态、实时心跳、邀请状态等高频热数据。

这样设计的原因是：

- 多人通话如果使用 mesh，每个客户端都要和所有人互连，人数一多带宽和 CPU 压力会迅速上升。
- SFU 转发更适合多人实时音视频，客户端只和服务端建立连接。
- LiveKit 这类成熟方案已经处理了很多 WebRTC 工程问题，比如多路转发、订阅管理、弱网适配、房间管理和录制扩展。
- 我保留自研信令和业务状态，媒体转发交给成熟服务，可以降低复杂度并提高稳定性。

面试时可以这样总结：

> 单人连麦和小规模连麦适合自己学习 RTC 链路，但多人视频通话更适合引入成熟 SFU。我的后续规划是业务层仍由自己的 Go 服务掌控，实时媒体层接入 LiveKit C++ SDK 和 LiveKit 服务端转发。

### 7.2 弹幕和评论规划

弹幕和评论可以按“实时热数据 + 持久化数据”拆开。

弹幕适合这样设计：

- 用户发送弹幕后，服务端先校验登录态、直播间状态和内容合法性。
- Redis 保存近期弹幕热数据，例如最近 N 条弹幕、房间弹幕流、在线用户临时状态。
- WebSocket 或 SSE 将弹幕实时推给观看端。
- MySQL 异步或同步持久化弹幕记录，保留用户、房间、视频时间点、内容、发送时间等信息。

评论适合这样设计：

- 评论更偏长期内容，MySQL 做主存储。
- Redis 可缓存热门评论、评论计数、近期回复等高频读取数据。
- 点赞、评论、弹幕都围绕 `user_id + video_id/room_id` 的关系建模，和当前点赞设计保持一致。

面试时可以强调：

> Redis 不替代 MySQL。Redis 用来承载高频实时读写和短期热数据，MySQL 负责最终一致的业务持久化。弹幕是实时流，评论是长期内容，两者的数据模型和缓存策略要分开。

### 7.3 直播录制规划

后续推流端可以增加“开始录制/停止录制”能力，但录制任务不建议由主播端本地直接完成，而是交给后端统一编排。

规划链路是：

1. 主播端在开播过程中选择开始录制。
2. 主播端向后端提交录制请求。
3. 后端校验主播身份、直播间状态和当前推流状态。
4. 后端启动录制任务，可以基于 LiveKit Egress、SRS 录制能力或 FFmpeg 拉流录制。
5. 录制任务运行过程中，后端记录录制状态、开始时间、输出文件、错误信息。
6. 录制完成后，文件保存到服务端或对象存储。
7. 后端生成录制记录和下载地址。
8. 主播端通过接口查看录制列表并下载录制文件。

这个设计的好处是：

- 主播端不用承担额外录制编码压力。
- 录制任务由服务端统一管理，便于失败重试、权限控制、文件归档。
- 录制文件可以和点播系统复用同一套对象存储、转码、封面和下载体系。
- 后续可以扩展为直播回放、精彩片段、自动转点播。

面试时可以这样讲：

> 录制本质上是服务端媒体任务，不应该只做成本地保存按钮。主播端只发起录制意图，后端负责启动录制、记录状态、保存文件和提供下载，这样更符合平台化设计。

### 7.4 Redis 和 MySQL 的分工

后续平台会把 Redis 和 MySQL 的职责区分得更清楚：

- Redis：在线人数、房间成员心跳、弹幕热流、麦位临时状态、邀请超时、热门计数缓存。
- MySQL：用户、视频、评论、点赞关系、直播房间、连麦记录、录制记录、录制文件元信息。

可以总结：

> 高频、短生命周期、可重建的数据放 Redis；需要审计、查询、长期保留的数据放 MySQL。Redis 提升实时体验，MySQL 保证业务结果可追溯。

## 8. 面试 Q&A 速记

### 你这个项目最大的亮点是什么？

不是单点功能，而是完整链路。点播有上传、转码、HLS、SSE、播放；直播有采集、编码、RTMP、HTTP-FLV、自研拉流解码；连麦有状态机、WebSocket 信令、RTC 媒体和混流分发。并且在直播观看里做了背压、丢帧和音频主时钟同步。

### 为什么要做背压？

实时流里生产速度和消费速度经常不一致。没有背压，队列会无限堆积，延迟越来越高，内存也不可控。背压是让上游根据下游水位减速，保证系统稳定和延迟可控。

### 为什么要丢帧？

直播追求当前性。迟到帧如果继续显示，只会让画面越来越落后。合理丢弃迟到帧，可以让播放追上当前时钟，保证低延迟观看体验。

### 为什么用 SSE？

点播转码状态是服务端单向通知，不需要复杂双向通信。SSE 比轮询实时，比 WebSocket 轻，适合视频状态和房间状态更新。

### 为什么连麦要状态机？

连麦涉及多个端和多轮异步消息，没有状态机会出现重复接受、取消后又收到接受、RTC 消息串到旧会话等问题。状态机能让每个动作在什么阶段合法变得明确。

### 为什么观众不直接走 WebRTC？

WebRTC 适合少数人互动，观众分发更适合单路 HTTP-FLV/HLS。把互动和分发拆开，主播和嘉宾低延迟互动，观众只拉一路节目流，平台更容易扩展。

### 点赞为什么不只存一个数字？

只存数字不知道谁点赞，也防不住重复点赞。存用户和视频的关系，既能统计总数，也能判断当前用户是否点过赞，还能扩展我的点赞和推荐特征。

### 后续多人视频通话准备怎么做？

我不会继续用全客户端 mesh 硬扩，而是考虑接入 LiveKit 这类成熟 SFU。业务服务负责房间、权限、token 和状态，LiveKit 负责多人音视频转发。Redis 存在线状态和临时房间热数据，MySQL 存房间、成员、通话和录制记录。

### 弹幕评论为什么要 Redis + MySQL？

弹幕实时性强、写入频繁，适合 Redis 做房间热流和近期弹幕缓存；评论和弹幕历史需要长期查询和审计，所以落 MySQL。Redis 提升实时体验，MySQL 保证最终持久化。

### 录制怎么设计？

主播端只发起录制请求，后端负责启动录制任务、跟踪状态、保存文件并生成下载地址。录制可以接 LiveKit Egress、SRS 录制或 FFmpeg 拉流录制，完成后复用点播存储体系，主播端再下载。

## 9. 收尾总结

这个项目可以重点突出三种能力：

第一是音视频链路能力：点播、直播、推流、拉流、解码、渲染、同步。

第二是实时系统能力：背压、队列、水位、丢帧、时钟、延迟控制。

第三是平台工程能力：用户体系、互动关系、SSE/WebSocket、状态机、虚拟机 Docker 部署、媒体服务组合。

面试时不要只说“我做了一个短视频平台”，要说：

> 我把一个音视频平台拆成点播资产管线、直播实时链路、连麦互动链路和客户端播放体验四个部分，并且每个部分都围绕音视频工程问题做了设计。
