# 《项目介绍与亮点梳理》

> 说明：本文基于当前仓库真实代码与文档整理，重点参考了 `README.md`、`docs/点播.md`、`docs/server上传到播放闭环梳理-20260325.md`、`docs/直播HTTP-FLV主链路实现说明-20260327.md`、`docs/直播卡顿修复.md`，以及 `frontend/`、`backend/`、`server/` 下的现有源码。未能从代码和文档中明确确认的内容，统一放到“待确认事项”。

# 1. 项目是什么

这个项目不是一个以后台管理、表单和接口增删改查为主的普通业务系统，而是一个面向音视频工程学习与求职展示的“短视频平台原型”。它同时覆盖了三条主线：桌面端短视频平台能力、点播媒体处理闭环、以及直播观看链路。当前阶段的项目定位，更准确地说是“短视频平台 + 自研播放器链路 + HTTP-FLV 直播观看能力”，其中最有技术含量的部分集中在 `backend/playerEngine/`、`backend/playercontroller/`、`backend/liveplayer/` 与 `server/` 的点播处理链路。

从工程组织上看，项目采用“Qt/C++ 桌面客户端 + Go 服务端”的组合：`frontend/` 和 `backend/` 负责桌面端 UI、控制器与播放器能力，`server/` 负责上传、入库、转码、对象存储访问、播放地址分发与状态通知。这意味着它不是只会“调接口播视频”，而是已经把上传、转码、播放、直播拉流、解码、渲染这些关键链路拆开并落到了真实代码里。

# 2. 项目当前已完成的内容

## 2.1 已完成

- 点播上传到播放闭环已经打通。真实链路可从 `frontend/pages/UploadPage/UploadPage.cpp` 的 `submitUpload()`，一路跟到 `server/cmd/api/main.go` 的 `handleVideoUpload()`、`server/internal/ingest/ingest.go` 的 `IngestLocalFile()`、`server/cmd/worker/main.go` 的 `claimPendingJob()` / `processJob()` / `markVideoReady()`，最后回到 `frontend/pages/HomePage/HomePage.cpp`、`frontend/widgets/MainWindow.cpp` 和 `frontend/widgets/VideoPlayerWindow.cpp` 完成播放入口。
- 点播播放器链路已经具备真实可运行的控制层和内核层。`backend/playercontroller/service/PlayerController.cpp` 已经接通 `openMedia()`、`openMediaWithIjkPlayer()`、`requestSeek()`、`requestSetVolume()`、`handleVideoFrame()`；底层 `backend/playerEngine/IjkMediaPlayer.cpp` 和 `backend/playerEngine/FFplayer.cpp` 已经包含 `ffp_prepare_async_l()`、`stream_open()`、`video_refresh_thread()`、`audio_decode_frame()`、`ffp_seek_to_l()`、`compute_target_delay()`、`get_master_clock()` 等关键逻辑。
- HTTP-FLV 直播观看主链路已经打通，而且不是把 URL 直接交给黑盒播放器。当前仓库中可确认的链路是：`backend/liveplayer/protocol/HttpFlvStreamReader.cpp` 读 HTTP 字节流，`backend/liveplayer/protocol/FlvDemuxer.cpp` 增量拆 FLV tag，`backend/liveplayer/decode/FlvVideoDecoder.cpp` 解 H.264，`backend/liveplayer/session/LivePlayerSession.cpp` 做队列管理和渲染调度，最后由 `frontend/widgets/VideoOpenGLWidget.cpp` 用 OpenGL 显示 YUV 帧。
- 直播观看相关的 AAC 解码、PCM 输出、视频队列、音频时钟、渲染 tick、晚到帧丢弃、未来帧裁剪、读流与解码背压，这些能力已经能在源码中找到真实实现。对应文件包括 `backend/liveplayer/decode/FlvAudioDecoder.cpp`、`backend/liveplayer/audio/SdlAudioOutput.cpp`、`backend/liveplayer/session/LiveAudioDecodeWorker.cpp`、`backend/liveplayer/session/LiveVideoDecodeWorker.cpp`、`backend/liveplayer/session/VideoFrameQueue.hpp`、`backend/liveplayer/session/LivePlayerSession.cpp`。
- 平台侧基础能力已经不是空壳。服务端已具备用户注册/登录/登出/会话校验（`server/cmd/api/auth.go`）、视频列表与详情（`server/cmd/api/main.go`）、点赞（`server/cmd/api/likes.go`）、SSE 事件推送（`server/cmd/api/events.go`）等能力。

## 2.2 部分完成

- 直播观看链路中的音频输出、音频主时钟与视频对齐，源码里已经进入可运行和调优阶段，但从文档和 UI 文案看，这一部分仍处于持续演进状态。`docs/直播HTTP-FLV主链路实现说明-20260327.md` 以及 `frontend/pages/StreamPage/StreamPage.cpp` 仍保留“下一阶段补 AAC / A/V sync”的描述，而当前 `backend/liveplayer/` 源码已经继续往前走了，这一差异需要在对外表述时谨慎处理。

- 点播平台的业务层已经具备首页、上传、点赞、播放入口和账户基础能力，但推荐、搜索、评论、弹幕、复杂审核、多码率自适应等平台能力，在当前仓库中没有看到已完成实现。

## 2.3 规划中

- 平台直播间业务闭环，包括房间态、开播态、观看态、房间内互动等。

# 3. 项目整体结构

## 3.1 目录与模块分工

- `app/`
  - 程序启动与装配层，负责把控制器、页面、窗口、播放器相关对象接起来。典型入口是 `app/bootstrap/AppBootstrap.cpp`。
- `frontend/`
  - Qt 前端层，负责页面和显示控件。
  - `frontend/pages/HomePage/`：视频流首页、详情拉取、SSE 更新、点赞。
  - `frontend/pages/UploadPage/`：视频上传入口。
  - `frontend/pages/StreamPage/`：直播观看入口页。
  - `frontend/pages/AccountPage/`：账户页。
  - `frontend/widgets/VideoPlayerWindow.cpp`：点播播放窗口。
  - `frontend/widgets/VideoOpenGLWidget.cpp`：YUV 帧渲染组件。
- `backend/playercontroller/`
  - 播放器控制层，负责把 UI 的打开媒体、播放、暂停、seek、音量、状态同步等高层事件桥接到播放器内核。核心类是 `PlayerController`。
- `backend/playerEngine/`
  - 点播播放器内核层。`IjkMediaPlayer` 负责消息循环与上层封装，`FFplayer` 负责更底层的解封装、解码、时钟、队列、刷新调度、seek 等核心逻辑。
- `backend/liveplayer/`
  - 直播观看链路。
  - `protocol/`：HTTP-FLV 读流与 FLV 增量拆包。
  - `decode/`：H.264 / AAC 解码。
  - `audio/`：SDL 音频输出与音频时钟。
  - `session/`：音视频 worker、队列、缓冲、render tick、背压控制。
  - `service/`：面向页面的 `LivePlayerController`。
- `server/`
  - Go 服务端。
  - `cmd/api/`：认证、视频列表、详情、上传、SSE、媒体对象分发。
  - `cmd/worker/`：异步转码 worker。
  - `cmd/importer/`：导入工具。
  - `internal/ingest/`：原视频入库和转码任务创建。
  - `internal/storage/`：MinIO 访问封装。
  - `internal/db/`：数据库初始化与局部 schema 保障。
- `docs/`
  - 设计说明、实现笔记、阶段文档、排查记录。它们和源码是互相印证的，不是单纯规划文档。

## 3.2 点播主要数据流

点播闭环当前可以概括为：

`UploadPage::submitUpload()`  
-> `handleVideoUpload()`  
-> `ingest.IngestLocalFile()`  
-> 原视频写入 MinIO `raw-media`、MySQL 写入 `videos` / `transcode_jobs`  
-> `worker` 通过 `claimPendingJob()` 抢任务  
-> `processJob()` 调 `ffprobe` / `ffmpeg` 生成 HLS 和封面  
-> 产物写入 MinIO `vod-media` / `image-assets`  
-> `markVideoReady()` 更新状态  
-> `notifyVideoUpdated()` / `publishVideoUpdated()` 推送 `video.updated`  
-> `HomePage::connectEventStream()` 刷新首页  
-> `MainWindow::connectPlaybackFlow()` 打开 `VideoPlayerWindow`  
-> `PlayerController::openMedia()`  
-> `IjkMediaPlayer::prepareAsync()`  
-> `FFPlayer::ffp_prepare_async_l()` / `stream_open()`

这里能看出，点播不是“前端上传后直接播本地文件”，而是已经形成了“对象存储 + 异步转码 + API 播放地址分发 + 客户端播放”的平台闭环。

## 3.3 直播观看主要数据流

当前直播相关代码的职责边界也比较清楚：

- 外部直播服务器负责 `RTMP ingest -> HTTP-FLV output`，这一点在 `docs/直播HTTP-FLV主链路实现说明-20260327.md` 中写得比较明确。
- 当前仓库负责消费 HTTP-FLV 并在 Qt 客户端内完成观看端链路。

仓库内真实链路是：

`LivePlayerController::openStream()`  
-> `LivePlayerSession::open()`  
-> `HttpFlvStreamReader::open()`  
-> `handleReaderDataChunk()`  
-> `FlvDemuxer::pushBytes()` / `drainParsedTags()`  
-> 音频 tag 进入 `AudioTagQueue`，视频 tag 进入 `VideoTagQueue`  
-> `LiveAudioDecodeWorker` / `LiveVideoDecodeWorker`  
-> `FlvAudioDecoder` / `FlvVideoDecoder`  
-> `SdlAudioOutput` / `VideoFrameQueue`  
-> `LivePlayerSession::onRenderTick()`  
-> `tryRenderNextQueuedVideoFrame()`  
-> `handleDecodedVideoFrame()`  
-> `VideoOpenGLWidget::presentFrame()`

这个结构说明项目已经把“直播观看”拆到了协议解析、解码、队列、调度和渲染层，而不是停留在页面上嵌一个现成播放器控件。

# 4. 播放器与直播链路梳理

## 4.1 点播播放链路

点播播放入口发生在前端首页和播放窗口之间：

- `frontend/pages/HomePage/HomePage.cpp` 中，`requestVideoDetail()` 会请求 `/api/videos/{id}`。
- `handleVideoDetailReply()` 会检查 `status` 是否为 `ready`、`playUrl` 是否存在。
- `frontend/widgets/MainWindow.cpp` 的 `connectPlaybackFlow()` 接收 `playRequested(...)`，创建或复用 `VideoPlayerWindow`。
- `frontend/widgets/VideoPlayerWindow.cpp` 的 `showSelectedVideo()` 会调用 `playerController_.openMedia(...)`。

控制层与内核层的调用链则是：

- `backend/playercontroller/service/PlayerController.cpp`
  - `openMedia()`
  - `openMediaWithIjkPlayer()`
  - `requestPlay()` / `requestPause()` / `requestSeek()` / `requestSetVolume()`
  - `syncPlaybackProgress()`
  - `handleVideoFrame()`
- `backend/playerEngine/IjkMediaPlayer.cpp`
  - `setDataSource()`
  - `prepareAsync()`
  - `start()` / `pause()` / `stop()` / `seekTo()`
  - `messageLoop()`
- `backend/playerEngine/FFplayer.cpp`
  - `ffp_prepare_async_l()`
  - `stream_open()`
  - `audio_decode_frame()`
  - `video_refresh_thread()`
  - `compute_target_delay()`
  - `get_master_clock()`
  - `ffp_seek_to_l()`

从代码结构看，`FFPlayer::stream_open()` 不只是“打开 URL”，而是会继续初始化音视频队列、时钟、读取线程、刷新线程等内部运行单元。这说明当前播放器链路已经触及 demux、decode、时钟与调度逻辑，而不是简单包一层第三方播放器 SDK。

## 4.2 HTTP-FLV 直播观看链路

当前直播观看能力的价值，主要体现在它是“拆开的、可学习的”。

- `backend/liveplayer/protocol/HttpFlvStreamReader.cpp`
  - 通过 `QNetworkAccessManager` 发起 HTTP 请求。
  - 在 `readyRead` 回调里持续拿 `QByteArray chunk`。
- `backend/liveplayer/protocol/FlvDemuxer.cpp`
  - 增量解析 FLV header、tag header、payload、`PreviousTagSize`。
  - 能识别 script/audio/video tag，也能识别 AVC/AAC sequence header。
- `backend/liveplayer/decode/FlvVideoDecoder.cpp`
  - 处理 H.264/AVC sequence header。
  - 从 FLV video tag 中取 NALU，送给 FFmpeg 解码。
- `backend/liveplayer/decode/FlvAudioDecoder.cpp`
  - 处理 AAC sequence header。
  - 把 AAC raw payload 送给 FFmpeg。
  - 解码后再重采样到 PCM。
- `backend/liveplayer/session/LivePlayerSession.cpp`
  - 负责 tag 分发、worker 管理、视频帧入队、渲染节拍、同步与背压。
- `frontend/widgets/VideoOpenGLWidget.cpp`
  - 负责把 YUV420P 帧用 OpenGL shader 转成可显示画面。

这一条链路的意义在于，项目已经把“直播观看”的学习重点落到了 `chunk -> FLV tag -> codec config -> packet -> frame -> render`，这比“把 FLV URL 丢给黑盒播放器就算直播功能完成”要扎实得多。

## 4.3 demux / decode / 队列 / render / 音视频同步

### 点播侧

- `FFPlayer` 内部能看到 `packet_queue_init`、`frame_queue_init`、`audioq`、`videoq`、`sampq`、`pictq`、`vidclk`、`audclk` 等典型音视频内核元素。
- `audio_decode_frame()` 说明音频解码不是缺席状态。
- `video_refresh_thread()`、`compute_target_delay()`、`get_master_clock()` 说明视频刷新与主时钟选择已经进入真实实现层。
- `ffp_seek_to_l()` 说明 seek 不是 UI 假动作，而是有底层处理入口。
- `PlayerController::handleVideoFrame()` 和 `VideoOpenGLWidget::presentFrame()` 说明渲染链路已经从内核帧走到了界面层。

### 直播侧

- `FlvDemuxer` 解决的是“HTTP-FLV 字节流如何正确切成 tag”的问题。
- `LiveAudioDecodeWorker` 与 `LiveVideoDecodeWorker` 说明音频、视频已经走了独立 decode worker。
- `VideoFrameQueue` 说明视频帧不是解出来就直接画，而是进入播放队列。
- `SdlAudioOutput::clockSnapshot()` 提供了音频时钟和缓冲快照。
- `LivePlayerSession::currentTargetVideoPtsMs()` 会在音频时钟可用时用音频做参考，在音频时钟不可用时退回 wall clock。
- `dropLateQueuedVideoFrames()`、`tryRenderNextQueuedVideoFrame()`、`maybeReanchorPlaybackClock()` 说明直播视频不是裸刷新，而是围绕目标 PTS 做调度和纠偏。

## 4.4 缓冲与背压控制

这一部分是最能说明项目“不是页面和接口项目”的地方。

在 `backend/liveplayer/session/LivePlayerSession.cpp` 中，可以明确看到几类和实时流媒体直接相关的控制逻辑：

- 启播缓冲：
  - `maybeStartBufferedPlayback()` 会在队列深度和缓冲时长达到阈值后再启动播放，而不是首帧一到就立即开跑。
- 目标时钟选择：
  - `currentTargetVideoPtsMs()` 会根据当前是否已有有效音频时钟，决定视频跟随音频还是跟随 wall clock。
- 晚到帧处理：
  - `dropLateQueuedVideoFrames()` 会主动丢弃已经错过显示时机的帧。
- 未来帧保留窗口：
  - `trimQueuedVideoFramesForPlaybackWindow()` 会裁剪过于超前的帧，避免队列长期堆积。
- 播放时钟重锚定：
  - `maybeReanchorPlaybackClock()` 会在非音频主时钟模式下，对超前严重的队列重新校准。
- 解码背压：
  - `updateDecodeBackpressure()` 会根据音频缓冲、视频队列深度和相对音频时钟的超前量，控制音频/视频 decode worker 的节奏。
- 入流背压：
  - `HttpFlvStreamReader::setReadThrottled()` 会通过 `QNetworkReply::setReadBufferSize(...)` 对入口读流做节流，避免上游数据持续压爆本地缓冲。

这类逻辑通常只会出现在真正处理流媒体链路的项目里，因为它们面对的是 PTS、缓冲厚度、解码速度、渲染节奏和网络 burst，而不是普通业务项目里的表单提交和数据库事务。

# 5. 项目亮点

## 5.1 亮点一：点播播放器不是单纯封装播放器控件，而是已经落到自研控制链和内核链

- 背景：项目的学习目标明确偏向音视频工程，尤其是播放器内核、demux、decode、A/V sync、seek 这类底层能力。
- 问题：如果只是把现成播放器控件嵌进页面，最多能证明“会调 SDK”，很难体现对底层播放链路的理解。
- 做法：当前项目通过 `PlayerController -> IjkMediaPlayer -> FFPlayer` 形成了完整的分层；`FFPlayer` 中已经出现 `stream_open()`、`audio_decode_frame()`、`video_refresh_thread()`、`compute_target_delay()`、`get_master_clock()`、`ffp_seek_to_l()` 等关键函数；`PlayerController::handleVideoFrame()` 负责把内核帧转成 `VideoOpenGLWidget` 可消费的 YUV 数据。
- 价值：这让项目的播放器部分具备了“能讲清楚打开媒体、解码、刷新、seek、状态回传”的深度，而不是只会在简历里写“接入 FFmpeg”。

## 5.2 亮点二：点播已经形成“上传 -> 转码 -> 分发 -> 播放”的真实闭环，而不是只有播放器 Demo

- 背景：短视频平台的价值不只在于能播，还在于内容如何进入系统、如何被处理、如何回到前端页面。
- 问题：很多个人项目只有“本地读一个视频文件”或“写个接口返回地址”，缺少平台闭环，技术含量容易被稀释。
- 做法：本项目已经把 `UploadPage::submitUpload()`、`handleVideoUpload()`、`IngestLocalFile()`、`claimPendingJob()`、`processJob()`、`markVideoReady()`、`publishVideoUpdated()`、`HomePage::connectEventStream()`、`VideoPlayerWindow::showSelectedVideo()` 串了起来；媒体文件会进入 MinIO，任务状态会落 MySQL，worker 会调用 `ffprobe` / `ffmpeg` 生成 HLS 和封面，客户端再通过 `/vod/...` 和 `/image/...` 播放与展示。
- 价值：这条链路让项目从“播放器实验”升级成“平台原型”，能够证明你理解了点播系统的媒体处理、异步任务和客户端回流机制。

## 5.3 亮点三：HTTP-FLV 直播观看不是把 URL 交给黑盒播放器，而是自己拆到了 chunk、tag、decode、render

- 背景：直播观看链路真正有价值的地方，在于对协议和码流结构的理解，而不是只会播放一个直播地址。
- 问题：如果直接把 HTTP-FLV URL 扔给现成播放器，很多底层细节都会被黑盒吞掉，无法体现对 FLV 封装和实时链路的理解。
- 做法：项目当前使用 `HttpFlvStreamReader` 接收 HTTP 字节流，使用 `FlvDemuxer` 增量解析 FLV header 和 tag，使用 `FlvVideoDecoder` 解析 AVC sequence header 与 NALU，再把解码后的视频帧交给 `LivePlayerSession` 和 `VideoOpenGLWidget` 渲染。
- 价值：这证明你并不是只会“配直播源”，而是已经深入到 FLV tag 级别去理解直播观看端的数据流。

## 5.4 亮点四：直播观看链路里已经出现了真实的“队列 + 缓冲 + 时钟 + 背压”设计

- 背景：直播观看最难的问题往往不是“能不能播第一帧”，而是网络 burst、解码过快、缓存失衡、音视频错位、卡顿和停画面这些运行时问题。
- 问题：只要开始处理实时流，光有“能收到包、能解码”远远不够，必须处理队列深度、启播阈值、时钟选择、晚到帧和 decode 速度控制。
- 做法：当前源码里已经有 `VideoFrameQueue`、`LiveAudioDecodeWorker`、`LiveVideoDecodeWorker`、`SdlAudioOutput::clockSnapshot()`、`maybeStartBufferedPlayback()`、`currentTargetVideoPtsMs()`、`dropLateQueuedVideoFrames()`、`trimQueuedVideoFramesForPlaybackWindow()`、`maybeReanchorPlaybackClock()`、`updateDecodeBackpressure()` 这些核心逻辑。
- 价值：这类实现最能体现你对流媒体播放“动态过程”的理解，也正是普通 CRUD 项目完全不会涉及的技术门槛。

## 5.5 亮点五：平台层已经开始考虑媒体分发边界与异步状态回流，而不是把对象存储地址直接暴露给客户端

- 背景：短视频平台一旦进入上传、转码、存储和播放环节，客户端拿到什么地址、如何感知转码完成，都会影响后续演进空间。
- 问题：如果直接返回 MinIO 裸地址，或者只能靠前端轮询猜状态，平台边界会很脆弱，后续接鉴权、代理、CDN 都会比较别扭。
- 做法：当前 `toVideoResponse()` 通过 `buildMediaURL()` 返回的是 API 自己的 `/vod/...` 和 `/image/...` 路径；`handleVODObject()`、`handleImageObject()` 由 API 代为读取 MinIO；同时 `events.go` 中实现了 SSE broker，客户端 `HomePage::connectEventStream()` 订阅 `video.updated` 来刷新状态。
- 价值：这说明项目不只是“能用”，而是已经开始沿着真实平台方向处理媒体分发边界和异步状态同步问题。

# 6. 项目最值得强调的技术点

- `backend/playerEngine/FFplayer.cpp` 中的 packet queue、frame queue、音视频时钟、video refresh、seek 入口。
  - 值得讲，因为这代表你不是只会调用播放器，而是已经进入播放器内核的核心抽象层。
- `backend/playercontroller/service/PlayerController.cpp` 对 UI 与播放内核的桥接。
  - 值得讲，因为它把“页面点击播放”翻译成“可维护的播放控制链”，能体现工程化能力，而不是把逻辑写死在窗口类里。
- `backend/liveplayer/protocol/FlvDemuxer.cpp` 的增量 FLV 拆包能力。
  - 值得讲，因为 HTTP-FLV 直播观看的关键门槛就在于字节流到 tag 的正确切分和状态维护。
- `backend/liveplayer/decode/FlvVideoDecoder.cpp` 与 `backend/liveplayer/decode/FlvAudioDecoder.cpp` 的 H.264 / AAC 解码路径。
  - 值得讲，因为它对应的是实际码流解码，而不是“播放器自动帮我播了”。
- `backend/liveplayer/session/LivePlayerSession.cpp` 里的启播缓冲、时钟选择、晚到帧丢弃、future trim、重锚定和背压。
  - 值得讲，因为这部分直接体现了你对实时播放稳定性的理解。
- `server/internal/ingest/ingest.go` 与 `server/cmd/worker/main.go` 的点播媒体处理闭环。
  - 值得讲，因为它把上传、入库、对象存储、转码、回写状态串成了真实平台链路。
- `server/cmd/api/events.go` 与 `frontend/pages/HomePage/HomePage.cpp` 的 SSE 状态回流。
  - 值得讲，因为它解决的是异步转码状态如何实时回到客户端，而不是只会做同步接口。

# 7. 这个项目和普通业务项目的区别

- 它的核心难点不在表结构和接口增删改查，而在“媒体数据怎么流动”。点播侧要处理上传、对象存储、异步转码、HLS 分发；直播侧要处理 HTTP-FLV 字节流、FLV tag、AAC/H.264 解码、队列、缓冲和时钟。
- 它包含明显的底层链路能力。`FFPlayer`、`FlvDemuxer`、`FlvAudioDecoder`、`FlvVideoDecoder`、`VideoFrameQueue`、`SdlAudioOutput` 这些模块说明项目已经触碰到播放内核和流媒体观看端，而不是停留在页面、接口和数据库。
- 它的技术门槛主要体现为“跨层联动和时间敏感逻辑”。很多问题不是调用一次函数就结束，而是要持续处理读流、拆包、解码、队列深度、PTS、主时钟、晚到帧、背压与状态回流，这和普通管理系统的复杂度完全不同。

# 8. 项目介绍的精简版

## 8.1 版本A：100~150字项目介绍

这是一个以音视频工程为核心的个人短视频平台项目，采用 Qt/C++ 构建桌面客户端，Go 实现点播服务端，已经打通上传、转码、HLS 分发、首页播放以及 HTTP-FLV 直播观看链路。项目重点不在 CRUD，而在自研播放器控制链、FLV 拆包、AAC/H.264 解码、队列缓冲、音视频时钟与背压控制等底层能力。

## 8.2 版本B：3~5条项目亮点总结

- 已打通点播上传到播放闭环，包含 MinIO 存储、MySQL 状态流转、worker 异步转码、HLS 分发和桌面端播放入口。
- 点播播放器不是简单封装控件，而是通过 `PlayerController -> IjkMediaPlayer -> FFPlayer` 落到了真实播放内核链路。

- 平台层已经具备 SSE 状态回流与 API 代理媒体分发边界，不是只把对象存储地址直接暴露给前端。
