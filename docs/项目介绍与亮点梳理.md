> 说明：这份文档不是按想象写的，而是按当前代码真实扫描结果整理。扫描范围包括：
>
> - 主平台仓库 `duanshipin-pingtai`
> - 连麦主播端仓库 `D:\itffmpeg\av_media\online\duanshipin-live-studio`
>
> 其中，`duanshipin-pingtai` 负责点播、直播观看、服务端房间与信令、可选混流；`duanshipin-live-studio` 负责主播端采集、预览、RTMP 推流、连麦状态机、RTC 媒体收发。下面的介绍以这两个仓库合并后的“完整项目”来写。

## 1. 项目定位

这是一个以**音视频工程能力**为核心的统一平台原型，不是一个以后台 CRUD 为主的管理系统。

它把三条原本容易割裂的链路真正打通了：

1. **点播链路**：上传原片、转码 HLS、列表展示、播放器播放。
2. **直播观看链路**：主播推 RTMP，观众走 HTTP-FLV，自研读流、拆包、解码、同步、渲染。
3. **直播连麦链路**：房间创建、成员管理、连麦申请/邀请、信令协商、WebRTC 建连、跨房混流、单路分发。

从工程角度看，这个项目的价值不在“页面有多少”，而在于它覆盖了：

- 播放器内核分层
- demux / decode / seek / A/V sync
- HLS 点播管道
- RTMP ingest 与 HTTP-FLV watch
- WebSocket 房间信令
- WebRTC 连麦媒体面
- 服务端混流与分发
- 多线程与多队列协同

## 3. 整个项目到底做了什么

### 3.1 点播闭环

用户在客户端上传视频后，服务端会把原片写入对象存储，并写入转码任务。后台 worker 抢占待处理任务，调用 FFmpeg 转码为 HLS，生成 `index.m3u8 + seg_xxx.ts`，再把状态回写数据库，并通过 SSE 通知前端刷新视频状态。前端收到 `video.updated` 后更新列表，用户点击即可播放。

这条链路涉及：

- 上传入口
- MinIO 原片存储
- MySQL 任务状态
- FFmpeg 转码
- HLS 分片
- API 列表分发
- SSE 异步刷新
- Qt 播放器加载播放

这说明项目不是“只会播本地文件”，而是具备完整的平台化点播媒体管道。

### 3.2 点播播放器内核

点播播放器不是简单调用现成控件，而是做了清晰的三层拆分：

- `PlayerController`：给 UI 提供稳定的控制接口
- `IjkMediaPlayer`：承接播放器状态、消息循环、生命周期管理
- `FFplayer`：真正负责 demux、decode、queue、clock、refresh、seek

这一层能够清楚讲出：

- 数据如何从 demux 进入音视频 packet queue
- 解码线程如何消费 packet
- frame queue 如何参与显示节拍
- seek 时为什么要 flush queue
- 为什么视频显示要跟主时钟走

### 3.3 直播观看链

观众侧没有直接依赖浏览器播放器，而是自己实现了一条 HTTP-FLV 播放链：

- `HttpFlvStreamReader` 负责读取 HTTP-FLV 字节流
- `FlvDemuxer` 负责拆出音视频 tag
- 音频、视频解码 worker 分线程工作
- 音频送到 `SdlAudioOutput`
- 视频进入 `VideoFrameQueue`
- `LivePlayerSession::onRenderTick()` 决定当前应该显示哪一帧
- `VideoOpenGLWidget` 在 GUI 线程中完成 YUV 上传和 OpenGL 渲染

这条链路的重点不是“能播”，而是“在实时流里如何控制缓冲、同步、丢帧和背压”。

### 3.4 主播端采集、预览与 RTMP 推流

在 `duanshipin-live-studio` 里，主播端实现了完整的本地采集与推流链：

- Windows 设备采集
- 本地预览
- H.264 编码
- AAC 编码
- RTMP 发送

`LiveSessionController` 负责把采集、预览、推流串起来。它不是把所有工作堆在一个线程里，而是拆成了：

- 采集/预览主工作线程
- 视频编码线程
- 音频编码线程
- RTMP sender 线程

采集到的媒体数据一边给本地预览，一边进入发布链路；如果正在连麦，还可以通过 media tap 直接复用这一路采集结果送给 RTC，而不是重新开一套摄像头和麦克风。

### 3.5 连麦系统

新增的连麦系统不是“聊天室按钮”，而是一个完整的业务态 + 实时态 + 媒体态组合：

- 业务态：谁申请、谁邀请、谁接受、谁挂断，落在数据库和 REST 接口里
- 实时态：谁在线、谁进房、谁收到邀请、谁开始协商，走 WebSocket 信令
- 媒体态：真正的音视频收发走 WebRTC `libdatachannel`

服务端并不是直接替用户做所有决定，而是通过：

- 房间
- 成员
- `linkmic_requests`
- `request_id`
- `session_id`
- `room_key`
- `user_id`

把“谁有资格和谁连麦”这件事约束得很明确。

### 3.6 混流与分发

连麦建立后，有两种可讲的观看模式：

1. **RTC 点对点/双向媒体通信**：适合连麦双方自己互动。
2. **服务端混流后单路分发**：适合观众观看。

项目里做了第二种能力。服务端在跨房连麦成立后，可以启动 FFmpeg 进程，从两路 RTMP 输入拉流，做视频拼接和音频混合，再生成一路新的 RTMP 输出。观众侧不需要同时拉两路，也不需要理解多路 RTC，只拉一路 HTTP-FLV 即可观看“合成后的连麦节目流”。

这就是从“连上了”走到“能被平台观看和分发”的关键一步。

## 4. 点播链路怎么实现

### 4.1 上传到转码

整体流程是：

1. 前端选择视频文件并发起上传。
2. 服务端接收 multipart 数据。
3. 原片进入对象存储。
4. 数据库中创建视频记录和转码任务。
5. worker 抢占 `pending` 任务。
6. worker 调用 FFmpeg 输出 HLS。
7. 转码成功后回写状态。
8. API 通过 SSE 推送 `video.updated`。
9. 前端刷新列表并允许播放。

这条设计的好处是把“上传接口响应速度”和“转码耗时”解耦了。上传成功不代表转码完成，前端通过 SSE 感知异步状态变化，体验比轮询更自然，也更接近真实媒体平台。

### 4.2 HLS 如何分片

在 `server/cmd/worker/main.go` 的 `transcodeToHLS` 中，FFmpeg 使用了典型的 VOD HLS 输出参数：

- `-c:v libx264`
- `-preset veryfast`
- `-crf 23`
- `-c:a aac`
- `-b:a 128k`
- `-f hls`
- `-hls_time 6`
- `-hls_playlist_type vod`
- `-hls_segment_filename seg_%03d.ts`

也就是：

- 输出编码为 H.264 + AAC
- 目标切片时长约 6 秒
- 主清单是 `index.m3u8`
- 分片文件是顺序递增的 `.ts`

为什么这样做：

- `libx264 + AAC` 兼容性最好，播放器与 CDN 都好接
- `6s` 分片是一个比较稳妥的 VOD 参数，兼顾请求数和起播体验
- `vod` playlist 说明这是完整点播资源，不是持续增长的 live playlist

这个方案的好处不是“参数多”，而是它足够标准，便于前端播放器、对象存储和后续扩展码率版本。

## 5. 点播播放器内核怎么实现

### 5.1 分层结构

播放器内部是典型的“控制层和内核层分离”：

- `PlayerController` 处理 UI 请求和进度同步
- `IjkMediaPlayer` 负责状态流转与消息转发
- `FFplayer` 负责真正的媒体处理

这样的分层带来两个直接好处：

- UI 不需要理解 FFmpeg 细节
- 内核可以围绕队列、时钟、线程独立演进

### 5.2 seek 怎么做

seek 不是“把播放位置变量改一下”这么简单。真实流程是：

1. 用户请求 seek
2. `IjkMediaPlayer` 记录 `state_before_seek_`
3. 内核发起 seek
4. 旧 packet / frame queue 被 flush
5. 新位置开始重新 demux / decode
6. seek 完成后按之前状态决定恢复播放还是暂停

这样做的原因是：

- 旧位置已经解码出来的包和帧不能继续用
- 如果不 flush，新的时间轴和旧缓存会混在一起
- UI 层仍然能保持“seek 前后状态连贯”

### 5.3 音视频同步怎么做

点播播放器的同步思路接近 `ffplay`：

- 音频或主时钟提供基准时间
- 视频根据当前帧 PTS 和主时钟差值计算显示时机
- `compute_target_delay` 决定下一帧应该等多久
- `video_refresh_thread` 按这个节拍刷新画面

这套方式的本质是：

- 视频不是“解码完就立刻显示”
- 它必须服从时钟
- 当时钟和帧时间有偏差时，要么等，要么丢，要么调整节奏

这才是真正意义上的 A/V sync。

### 5.4 点播背压怎么做

在 `FFplayer.cpp` 中，demux 线程并不会无限制地 `av_read_frame`。当音视频包队列已经足够大，或者缓冲已经达到“够播”的条件时，读线程会短暂休眠，等消费端追上来再继续读。

这就是最经典的**上游服从下游**设计。

它的好处是：

- 避免内存被 packet queue 撑爆
- 避免无意义地提前读太多数据
- 让解码和播放节奏跟实际消费能力对齐

## 6. HTTP-FLV 直播观看链怎么实现

### 6.1 基本链路

直播观看端的核心流程是：

1. 从 HTTP-FLV 地址读字节流
2. 拆出 FLV header 和 tag
3. 区分音频 tag、视频 tag、script tag
4. 分发到音频/视频解码 worker
5. 音频进入 SDL 播放
6. 视频进入帧队列
7. `onRenderTick()` 按时钟决定显示
8. OpenGL 组件在主线程绘制 YUV

这里最值得讲的不是协议本身，而是：

- 流是实时的，不能像文件那样任意缓存
- 网络、解码、渲染速度不稳定
- 所以系统必须主动做流控和同步

### 6.2 背压控制怎么做

这个项目的直播观看背压做得比较完整，不只是一个“队列满了就丢”。

#### 6.2.1 读流层背压

`HttpFlvStreamReader::setReadThrottled()` 会通过 `QNetworkReply::setReadBufferSize` 控制网络层缓冲。也就是说，当下游已经来不及处理时，最上游的 HTTP 读取就会被限流，而不是继续无上限吃数据。

好处：

- 防止 Qt 网络缓冲和中间层内存不断膨胀
- 让“堵”尽量发生在更靠上的地方

#### 6.2.2 解码层背压

`LivePlayerSession::updateDecodeBackpressure()` 会分别判断音频和视频是否该继续解码。

音频侧看的是：

- PCM 队列是否过厚
- 当前是否“音频饥饿”
- 是否已经有足够的音频缓冲

视频侧看的是：

- 视频队列深度
- 视频尾部 PTS 是否已经明显领先音频时钟
- 当前 buffered duration 是否过高

于是它不是简单的“满了就停”，而是有高低水位和滞回逻辑，避免系统在“开/关背压”之间频繁抖动。

#### 6.2.3 显示层自我修剪

即使进入了视频队列，也不代表一定会被显示。项目里还做了：

- `dropLateQueuedVideoFrames`
- `trimQueuedVideoFramesForPlaybackWindow`
- `maybeReanchorPlaybackClock`

也就是：

- 太晚的帧直接丢
- 太超前的帧不让它无限囤积
- 时钟飘了要重新锚定

整个直播观看端的核心思想是：

> 不追求“一个包都不丢”，而追求“延迟稳定、同步稳定、内存稳定”。

这比单纯强调“零丢帧”更符合直播系统的真实目标。

### 6.3 音视频同步怎么做

直播观看端一般优先以音频为主时钟，因为音频连续输出对人耳最敏感。项目里也是这个思路：

- `SdlAudioOutput` 提供音频时钟快照
- `currentTargetVideoPtsMs()` 用音频时钟推导视频目标显示点
- `onRenderTick()` 计算当前该不该显示某帧
- 如果视频晚了就丢
- 如果视频太快就等

好处：

- 声音不断裂
- 画面围绕声音调整
- 比“视频主时钟硬拉音频”更稳

### 6.4 为什么渲染不用单独线程，而是回调前端 OpenGL

这里是项目一个很好的工程取舍点。

`LivePlayerSession::handleDecodedVideoFrame()` 最终不是自己开渲染线程直接画，而是通过 `QMetaObject::invokeMethod` 把帧投递给 `VideoOpenGLWidget::presentFrame()`，由 widget 所在线程完成纹理上传和绘制。

为什么这样做：

1. `QOpenGLWidget` 的上下文天然和 GUI 线程绑定，跨线程直接画最容易出错。
2. 解码线程只负责“把可显示帧准备好”，不负责碰 UI 对象。
3. 同步节拍已经由 `onRenderTick()` 统一控制，再额外加一条独立渲染线程只会让时序更复杂。
4. 通过 GUI 线程 update/repaint，能更自然地接入 Qt 事件循环。

所以这里不是“不会多线程渲染”，而是明确选择了**媒体线程负责时序，GUI 线程负责 OpenGL 上屏**。这比盲目再起一个渲染线程更稳。

## 7. 主播端推流链怎么实现

### 7.1 采集与预览

主播端使用 Windows 采集能力完成摄像头和麦克风输入。`LiveDeviceCaptureSource` 负责设备接入，`LiveSessionController` 负责把采集结果送到预览界面和后续发布链。

这里的关键点是：

- 采集不是只为推流服务
- 同一份采集结果还要服务本地预览和 RTC 连麦

因此它不是“采一次用一次”，而是一个可复用的媒体源。

### 7.2 推流链

推流阶段大致是：

1. 采集线程拿到原始音视频帧
2. 视频进入 H.264 编码线程
3. 音频进入 AAC 编码线程
4. 编码结果进入 sender 队列
5. RTMP sender 线程封装并发送

项目中比较专业的一点是：推流前会先发送 H.264 sequence header 和 AAC sequence header，而不是裸推媒体帧。这意味着接入方更容易正确识别码流参数。

### 7.3 视频编码怎么做

主播端的视频编码是显式的 H.264 编码流程，不是“交给黑盒 SDK 就不管了”。

它会围绕：

- 分辨率
- 帧率
- 编码器初始化
- SPS/PPS
- 关键帧参数

完成一条真实的编码发送链。

在 RTC 侧，`RtcPeerSession` 也会在首帧到来时初始化 H.264 编码器，并在关键帧需要时补带参数集，这对远端正确解码很关键。

### 7.4 音视频时间戳怎么处理

`LiveSessionControllerPipeline.cpp` 里做了一个很关键但经常被忽略的工作：**发布时间轴归一化**。

它不是把采集侧墙上时间直接原样塞进网络，而是：

- 以发布起点建立 publish epoch
- 将视频帧映射到单调递增的发布 PTS
- 将音频编码单元的 PTS/DTS 归一化
- 保证输出时间戳单调、不回退

为什么这一步重要：

- 采集线程时钟和网络发送节拍不是一回事
- 如果时间戳不稳定，接收端更容易出现卡顿、抖动和不同步
- 统一发布时钟后，RTMP 与后续观看端都更容易消费

## 8. 连麦系统怎么实现

### 8.1 为什么要拆成“业务态 + 信令态 + 媒体态”

连麦是最容易被写乱的部分。这个项目之所以能讲清楚，是因为它没有把所有事情都塞进一个 WebSocket handler，而是明确分成三层：

1. **业务态**
   - 谁创建房间
   - 谁是主播
   - 谁申请连麦
   - 谁邀请谁
   - 谁接受、拒绝、取消、挂断
   - 这些状态落在 REST 和数据库里

2. **信令态**
   - 谁上线
   - 谁进房
   - 谁收到了邀请
   - 谁该发 offer
   - 谁该回 answer
   - 这些状态在 `/ws` 和内存 hub 里流转

3. **媒体态**
   - 真正的音频/视频 track 如何建连
   - ICE candidate 如何交换
   - 本地采集如何送入 PeerConnection
   - 远端流如何解包与预览

这样拆分之后，每一层的职责都更清楚，而且出问题时更容易定位到底是“业务没授权”、“信令没发到”还是“RTC 媒体没通”。

### 8.2 服务端房间与连麦 REST

`server/cmd/api/live_rooms.go` 负责房间和连麦业务操作。它提供的核心能力包括：

- 创建房间
- 查询房间详情
- 查询成员
- 上报在线状态
- 关闭房间
- 申请连麦
- 邀请连麦
- 接受/拒绝
- 取消
- 挂断

数据库中的 `linkmic_requests` 表会保存：

- `request_id`
- `room_id`
- `request_type`
- `state`
- `initiator_user_id`
- `target_user_id`
- `accepted_by_user_id`
- `ended_by_user_id`
- 时间戳
- 元数据

这意味着“连麦是不是已经发生过、现在处于什么阶段”有持久化依据，不会因为某个 WebSocket 断开就完全丢历史。

### 8.3 服务端为什么要用 `/ws` 信令

因为连麦和 RTC 协商不是一发一收的简单请求，而是多轮异步过程：

- 成员进入房间要立即通知别人
- 申请/邀请要即时到达
- accept 后双方要立刻收到 join params
- offer / answer / ice-candidate 要持续收发

如果全用 REST 模拟，会很别扭，也很难做实时房间成员感知。

所以项目里单独提供了 `/ws`，专门承担：

- 房间成员广播
- 连麦控制消息
- RTC SDP/ICE 中继

### 8.4 `probe.register` 为什么要这样设计

客户端连上 `/ws` 后，不是立刻就“默认有资格发所有消息”，而是先发 `probe.register`。这个注册消息里会带上：

- `room_id`
- `peer_id`
- `role`
- 在 RTC 场景下还会带 `request_id`

这么设计的原因是：

1. 服务端需要先把 socket 和“哪个房间里的哪个用户”绑定起来。
2. 后续 RTC 转发必须知道该把消息投给谁。
3. `request_id` 能把这个 WebSocket 连接绑定到一条已被接受的连麦业务记录上。

尤其是 `validateAcceptedRTCRegistration` 这步很关键：

- 它会查数据库确认请求状态已经是 `accepted`
- 确认这个请求确实属于当前房间
- 确认 `peer_id` 和业务上应该参与连麦的用户一致

好处是：

- 防止未授权用户伪造 peer 身份
- 防止有人跳过业务授权直接连 RTC
- 把“实时信令”牢牢绑在“已落库的业务结果”上

这是一种很适合平台项目的设计，不是纯 demo 式的“谁连上 WebSocket 谁都能发 offer”。

### 8.5 前后端状态机怎么协同

这个项目的连麦不是只靠后端判断，也不是只靠前端页面变量判断，而是前后端都用了状态机。

#### 8.5.1 服务端状态机

服务端在 `signaling.go` 里维护同房和跨房的连麦会话状态。比如：

- `pending`
- `accepted`
- `rejected`
- `cancelled`
- `connected`
- `ended`

对于同房连麦，内存里还有更细的会话阶段，例如：

- guest applying
- host inviting
- linkmic active

服务端会校验：

- 角色方向是否正确
- 当前状态下能不能执行这一步
- 房间里是否已经存在活跃会话

因此不会轻易出现：

- 重复 accept
- 非主播接受自己的邀请
- 同一房间同时起多条互斥连麦

#### 8.5.2 主播端状态机

主播端 `LinkMicRoomState` 里也定义了清晰状态：

- `idle`
- waiting response
- incoming invite
- waiting join params
- rtc joining
- rtc connected
- ending

`LinkMicSession` 负责：

- 发起 invite
- 处理 apply/invite/accept/reject/cancel/hangup
- 等待超时
- 保存 `rtc.join-params`
- 在合适时机启动 RTC

这样做的好处是：

- UI 不需要直接理解 SDP/ICE
- 业务流程和媒体流程解耦
- 状态转移有边界，不容易出现按钮乱点导致的时序错误

#### 8.5.3 为什么状态机有价值

前后端都用状态机的核心收益是：

- **可推理**：知道当前系统处于哪一步
- **可拒绝非法输入**：不合法动作可以明确拒绝
- **可恢复**：断线、超时、取消时更容易回退
- **可日志化**：状态迁移天然适合打点和定位问题

对于连麦这种“跨端、多线程、异步消息密集”的系统，这个收益非常大。

### 8.6 主播端和服务端如何交互

主播端的 `BusinessLiveClient` 会先通过 HTTP 侧完成登录和房间准备，然后把 API base URL 推导成 WebSocket signaling URL，并接入 `/ws`。

连接建立后，它会发送：

- `live.anchor.join`
- 定时 `live.anchor.heartbeat`
- 必要时 `live.anchor.leave`

随后一条业务 WebSocket 上就会承载：

- 房间成员变更
- 连麦业务消息
- RTC offer/answer/candidate

为什么这样做：

- 不用再单独维护第二套“业务 socket”和“RTC socket”
- 房间 presence、连麦状态、RTC 协商在同一条连接里天然保持时序一致
- 客户端可以基于同一个连接状态判断自己是否在线、是否可连麦

这也是主播端工程里一个很好的设计点。

### 8.7 RTC 媒体如何建立

当业务态走到 accept 后，服务端会给双方下发 `rtc.join-params`。其中会明确：

- `sessionId`
- `requestId`
- `roomAKey / roomBKey`
- `selfRoomKey / peerRoomKey`
- `selfUserId / peerUserId`
- `businessRole`
- `rtcRole`
- `signalingUrl`
- `iceServers`
- `rtcBackend`
- `mediaMode`

这一步很重要，因为它把：

- 业务世界里谁邀请谁
- RTC 世界里谁发 offer 谁回 answer

统一到了一个明确的参数对象中。

主播端收到 `rtc.join-params` 后，会：

1. 创建 `RtcSessionConfig`
2. 启动 `RtcSignalingBridge`
3. 启动 `RtcPeerSession`
4. 把本地音视频通过 media tap 或 fallback capture 送入 RTC
5. 交换 `offer` / `answer` / `ice-candidate`
6. 建立收发 track

### 8.8 RTC 信令桥为什么要单独做

`RtcSignalingBridge` 不是多余层，它的作用是把“业务 WebSocket 消息”和“RTC 协商消息”隔开。

它会严格检查：

- `sessionId`
- `fromRoomKey`
- `toRoomKey`
- `fromUserId`
- `toUserId`
- `requestId`

只有命中当前会话的消息才会继续交给 `RtcPeerSession`。

好处：

- 同一条 WebSocket 上可以承载很多类消息而不串线
- 多房、多会话共存时更安全
- 调试时更容易定位是信令路由错了还是媒体没通

### 8.9 为什么 RTC 优先复用现有采集，而不是重新开设备

主播端已经有一套采集给预览和 RTMP 推流。如果连麦时再单独开一次摄像头和麦克风，会带来很多问题：

- 设备独占冲突
- 两套采集时间轴不一致
- CPU/内存成本上升
- 预览画面和连麦画面可能不一致

所以项目里通过 `setMediaTapCallbacks` 把已经存在的采集结果直接旁路给 RTC。这样一来：

- 预览、推流、RTC 用的是同一份源
- 设备只开一次
- 时间基更统一
- 架构更清晰

如果某些场景不能复用，`RtcPeerSession` 也保留了 fallback capture，鲁棒性更好。

### 8.10 RTC 内部多线程怎么协调

`RtcPeerSession` 自己也不是单线程：

- PeerConnection 信令与回调线程
- 本地视频发送线程
- 本地音频发送线程
- 可选本地采集线程
- 远端音频 sink
- 远端视频 sink

它内部为音频和视频都用了有界队列。当本地输入速度超过发送/编码速度时，会丢弃最旧帧而不是无界堆积。

这跟直播观看端的背压思想是统一的：

> 实时媒体系统首先要保证“系统活着”，然后才是“尽量保真”。

## 9. 混流和分发怎么实现

### 9.1 为什么要做服务端混流

如果只做连麦双方的 RTC 通话，那么“主播能连上”这件事已经成立了。但平台要让大量观众方便观看，还需要解决一个问题：

> 观众看什么？

如果让每个观众自己同时订阅多路 RTC：

- 播放端复杂
- 终端兼容难
- CDN 分发不友好
- 录制也麻烦

所以项目里增加了服务端混流。

### 9.2 混流具体怎么做

`server/internal/linkmicmix/manager.go` 中，FFmpeg 会从两路 RTMP 输入拉流：

- 自己一路
- 对端一路

视频部分会先做缩放与补边，然后用 `xstack` 把两路画面拼在一个画布上。音频部分会先 `aresample=async=1:first_pts=0`，再用 `amix` 混音。

随后再编码为：

- `libx264`
- `-preset veryfast`
- `-tune zerolatency`
- `yuv420p`
- AAC 48kHz 立体声

最后以 FLV over RTMP 形式输出。

### 9.3 为什么这样做

这个设计的好处有三点：

1. **观众端简单**
   - 只拉一路 HTTP-FLV 即可
   - 不需要理解双流排版

2. **平台侧可控**
   - 可以统一布局
   - 可以统一码率
   - 后续容易接录制、审核、转推

3. **链路分工明确**
   - RTC 解决“主播和嘉宾怎么通”
   - 混流解决“平台怎么播给观众看”

### 9.4 为什么音频要先重采样再混

两路主播的音频虽然都在“实时说话”，但它们的采集时钟、编码时钟、网络到达时钟不可能完全一样。如果直接硬混，很容易出现：

- 轻微漂移
- 卡顿
- 爆音
- 时间基不齐

因此项目里先做 `aresample=async=1:first_pts=0`，再做 `amix`。本质上是在混之前先让两路音频尽可能回到一个可对齐的时间基上。

这也是一个很能体现音视频工程意识的细节。

## 10. 服务端能力怎么讲

### 10.1 认证

服务端不是第三方 OAuth 登录，而是自建账号 + Bearer 会话令牌模型。

它的核心流程是：

- 注册时对密码做带 salt 的 hash
- 登录成功后创建 session token
- token 写入 `user_sessions`
- 受保护接口走 `Authorization: Bearer`

这样做的优点是实现简单、桌面端接入轻量、适合原型平台；如果以后要接微信、GitHub 或企业 SSO，再在这一层外面扩 OAuth 即可。

### 10.2 视频列表

服务端会输出视频列表和详情，前端首页可以基于这些接口展示转码结果、封面、标题、播放入口等信息。这个部分本身不是项目最难的地方，但它把媒体管道的结果真正落到了“可见的产品形态”上。

### 10.3 上传

上传并不是“接口收到文件就结束”，而是平台媒体入口：

- 收文件
- 存原片
- 建记录
- 建转码任务
- 触发异步处理

这说明服务端已经不只是一个业务壳，而是真正承担了媒体资产生命周期的第一段。

### 10.4 SSE

SSE 在这个项目里不只是“加了个新技术点”，而是用于把异步媒体状态推回前端。

现在至少能看到两类实时事件：

- `video.updated`
- `linkmic.room.updated`

这带来的好处是：

- 视频转码完成后前端立即感知
- 房间状态变化时页面不必疯狂轮询
- 前端体验和服务端异步处理节奏更贴合

## 11. 多线程是怎么协调的

### 11.1 点播播放器

点播播放器内部典型是：

- demux/read 线程
- 音视频解码消费路径
- video refresh 线程
- packet queue / frame queue 协调

核心是“线程之间不直接互相控制 UI”，而是通过队列和时钟驱动。

### 11.2 直播观看端

直播观看侧涉及：

- HTTP 读流
- FLV demux
- 音频解码 worker
- 视频解码 worker
- GUI render tick
- OpenGL 绘制

它的关键不是线程多，而是：

- 每条线程只做自己最擅长的事
- 边界靠队列和回调而不是互相抢锁

### 11.3 主播端

主播端涉及：

- 采集/预览工作线程
- 视频编码线程
- 音频编码线程
- RTMP sender 线程
- RTC 音视频发送线程
- PeerConnection 回调线程

这里最核心的工程意识是：

- 采集、编码、发送分离
- 每一段之间用有界队列解耦
- 上游不能无限把压力灌给下游

所以这个项目的多线程不是“线程越多越高级”，而是“按照媒体处理阶段自然拆分，并用背压维持稳定”。

## 13. 精简版项目介绍

### 13.1 一段话版

这是一个 Qt/C++ + Go 的统一音视频平台原型，完整打通了点播上传转码播放、HTTP-FLV 直播观看、主播端 RTMP 推流、房间连麦信令、WebRTC 音视频交互，以及跨房连麦后的服务端混流分发。项目重点不在通用业务，而在播放器内核、背压控制、音视频同步、状态机、信令路由和多线程媒体管线这些音视频工程核心能力。

## 14. 如何验证这份介绍和代码一致

最小验证建议如下：

1. **点播**
   - 上传一个短视频
   - 检查 worker 是否生成 `index.m3u8` 和 `.ts`
   - 检查前端是否收到 `video.updated`

2. **直播观看**
   - 让主播端推一路 RTMP
   - 通过 HTTP-FLV 地址在观看端播放
   - 观察 `audio_backpressure`、`av_sync` 相关日志

3. **房间与连麦**
   - 创建房间
   - 发起一次 apply 或 invite
   - accept 后观察 `/ws` 中是否有 `rtc.join-params`

4. **RTC 媒体**
   - 在 `duanshipin-live-studio` 侧启动主播端
   - 检查本地预览、远端预览和 ICE/SDP 交换

5. **混流**
   - 开启 `LINKMIC_MIX_ENABLE=true`
   - 跨房连麦 accept 后检查是否生成 mixed output
   - 用观众端拉取对应 HTTP-FLV 地址

如果这些链路能跑通，这份项目介绍里的绝大多数关键表述都能在真实代码和真实行为里对应上。
