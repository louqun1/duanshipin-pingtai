# 点播用户服务端接入

## 1. 文档目的

这份文档用于总结当前点播系统在“用户系统服务端化”这一阶段的设计思路和落地结果。

重点不放在代码细节，而放在三件事：

- 为什么用户系统必须接入服务端
- 当前整体架构已经变成什么样
- 后续点赞、弹幕、视频归属应该基于什么继续扩展

---

## 2. 为什么要把用户系统放进服务端

在只有本地客户端登录时，用户身份只存在于客户端本地，无法成为真正的业务主身份源。

这会直接带来几个问题：

- 服务端不知道“这个视频是谁上传的”
- 换一台设备后，无法识别是不是同一个用户
- 点赞、收藏、弹幕这类数据无法稳定关联到统一用户
- 后续接口鉴权会越来越混乱

所以点播系统进入“上传闭环”之后，下一步最合理的主线不是继续优化上传页面，而是把用户系统迁入服务端。

一句话概括：

用户登录、会话、上传归属、点赞、弹幕，这些都应该以服务端用户 ID 为准。

---

## 3. 当前设计思路

整体思路是：

1. 把用户身份源放到服务端 MySQL
2. API 提供登录、注册、注销、当前用户接口
3. Qt 客户端不再依赖本地 SQLite 作为主认证来源，而是调用服务端 auth 接口
4. 登录成功后，客户端保存服务端返回的 token
5. 上传视频时带上 bearer token，由服务端识别当前用户并写入 `videos.user_id`
6. 视频列表和详情接口返回上传用户信息，首页可直接显示“是谁上传的”

这样做的意义是：

- 视频归属被正式打通
- 后续点赞表、弹幕表都能直接关联 `user_id`
- 用户体系不再分裂成“客户端本地用户”和“服务端业务用户”两套

---

## 4. 当前整体架构

当前主链路可以概括为：

```text
Qt AccountPage
  -> AuthController
  -> API /api/auth/*
  -> MySQL users / user_sessions

Qt UploadPage
  -> Bearer Token
  -> API /api/videos/upload
  -> MySQL videos / transcode_jobs
  -> MinIO raw-media
  -> Worker
  -> MinIO vod-media / image-assets
  -> API /api/videos / /api/videos/{id}
  -> Qt HomePage

Worker
  -> API internal notify
  -> API SSE /api/events
  -> Qt HomePage refresh
```

可以把它理解成两条主线：

- 认证主线：客户端登录 -> 服务端签发会话 -> 客户端保存 token
- 点播主线：客户端上传 -> 服务端识别用户 -> 视频入库转码 -> 首页展示上传者与封面

---

## 5. 当前主要接口

### 5.1 用户认证接口

当前主要认证接口如下：

- `POST /api/auth/register`
  用于注册新用户，并在注册成功后直接建立会话

- `POST /api/auth/login`
  用于用户登录，返回当前用户信息和访问 token

- `POST /api/auth/logout`
  用于注销当前会话

- `GET /api/me`
  用于根据当前 token 读取当前登录用户

这些接口构成了服务端用户系统的最小闭环。

### 5.2 点播相关接口

- `POST /api/videos/upload`
  现在要求带 `Authorization: Bearer <token>`，服务端会把当前登录用户写入视频归属

- `GET /api/videos`
  返回视频列表，当前已包含上传用户信息，可用于首页展示

- `GET /api/videos/{id}`
  返回单个视频详情，也包含上传用户信息

- `GET /api/events`
  用于 SSE 推送视频状态变化，上传完成后首页可以自动更新

---

## 6. 当前数据关系

从业务角度看，当前最重要的关系已经明确：

- 一个用户可以上传多个视频
- 一个视频归属于一个上传用户
- 一个用户会拥有多个登录会话

也就是说，当前已经从“只有视频”升级成了“用户 + 视频”的结构。

这一步是后续所有互动能力的基础。

---

## 7. 这一步解决了什么问题

接入服务端用户系统之后，当前已经解决了这些关键问题：

- 登录态不再只存在于客户端本地
- 上传接口可以识别“当前是谁在上传”
- 视频记录可以正式关联上传者
- 首页可以显示上传用户名
- 后续扩展点赞、弹幕、收藏时，不需要再重做用户底座

所以这一步不是“上传优化”，而是整个点播系统从“媒体处理原型”走向“真实业务系统”的关键节点。

---

## 8. 对后续功能的意义

这一步完成后，后续几个能力就都有了统一落点：

### 8.1 视频归属

视频可以明确知道：

- 是哪个用户上传的
- 将来属于哪个用户的作品列表

### 8.2 点赞

后续可以直接设计：

- 用户点赞了哪个视频
- 一个用户是否已经点赞过某个视频
- 某个视频总共有多少点赞

### 8.3 弹幕

后续也可以直接设计：

- 哪个用户发了弹幕
- 弹幕属于哪个视频
- 弹幕内容是什么
- 弹幕出现在哪个播放时间点

也就是说，点赞和弹幕都不应该先做在客户端本地，而应该建立在服务端用户体系上。

---

## 9. 当前实现边界

当前这次接入的目标是：

- 先把服务端用户系统打通
- 先把上传归属打通
- 先让客户端登录真正依赖服务端

当前还没有继续展开的内容包括：

- 点赞接口
- 弹幕接口
- 收藏接口
- 用户作品页
- 权限分级

这些都属于下一阶段在当前用户底座上继续扩展的内容。

---

## 10. 下一步建议

在当前“用户系统服务端化”已经落地之后，最合理的下一步不是回头继续抠上传小细节，而是直接进入互动数据设计。

建议顺序如下：

1. 先补 `video_likes`
   打通“哪个用户点赞了哪个视频”

2. 再补 `video_danmaku`
   打通“哪个用户在什么时间点发了什么弹幕”

3. 再补“我的视频 / 我的点赞 / 我的弹幕”
   让用户页真正和点播数据产生关联

如果只选一个 next step，最推荐先做点赞，因为它比弹幕更简单，也能最早验证“用户和视频关系”是否设计正确。

---

## 11. 总结

点播上传闭环完成之后，用户系统接入服务端是非常自然的一步。

它的本质不是“把登录接口补一下”，而是把整个系统的业务主身份源从客户端本地迁移到服务端。

完成这一步之后，系统就具备了继续向下面这些方向扩展的基础：

- 视频归属
- 点赞
- 弹幕
- 收藏
- 用户作品页
- 更完整的权限控制

所以这一步可以理解为：

点播系统已经从“能上传、能转码、能播放”进入到“可以承载真实用户行为”的阶段。
