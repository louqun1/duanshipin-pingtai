### 1.4 一个重要现状

当前 `server` 代码里：
- 会自动确保的表只有 `users / user_sessions / video_likes`，见 `server/internal/db/schema.go`
- `videos / transcode_jobs` 的建表 SQL 不在运行时代码里，而是在部署文档里，见 `docs/点播第一阶段部署.md:262`、`docs/点播第一阶段部署.md:282`

这意味着：
- 当前服务运行前，`videos / transcode_jobs` 需要先按部署文档建好
- 当前“队列”是 MySQL 表 `transcode_jobs`
- 当前没有 Redis 真正参与上传到播放闭环

## 2.2 这条闭环里实际经过的表

核心表：
- `videos`
- `transcode_jobs`

上传/查询支撑表：
- `users`
- `user_sessions`
- `video_likes`

其中各表作用：
- `videos`
  - 存视频元数据、源文件 key、播放 key、封面 key、状态、宽高、时长、错误信息
- `transcode_jobs`
  - 当前实际队列表
  - 用 `status = pending/running/success/failed` 驱动 worker
- `users`
  - 上传者信息、列表页/详情页展示上传者用户名
- `user_sessions`
  - 上传接口鉴权
- `video_likes`
  - 首页和详情页查询时一并统计 `likeCount / likedByMe`

## 2.3 这条闭环里实际经过的 MinIO bucket

- `raw-media`
  - 原视频上传目标
  - worker 下载源视频的来源 bucket
- `vod-media`
  - HLS 播放清单和 ts 分片上传目标
  - API `/vod/*` 的读取来源
- `image-assets`
  - 封面上传目标
  - API `/image/*` 的读取来源

## 2.4 这条闭环里实际经过的 Redis key

当前实现里没有：
- 没有 Redis client
- 没有 Redis queue
- 没有 Redis key

当前“入队/出队”完全依赖：
- MySQL `transcode_jobs` 表
- worker 轮询 + 事务抢占

## 3. 按时间顺序的一条 sequence

下面按“上传 -> 入库 -> 入队 -> 转码 -> 产物上传 -> ready -> API 查询 -> Qt 播放”写成文字版 sequence。

### 3.1 API 上传路径

1. Qt 上传页 `UploadPage::submitUpload()` 组装 multipart，请求 `POST /api/videos/upload`
2. API `handleVideoUpload()` 校验 Bearer Token
3. `requireAuthenticatedUser()` 通过 `user_sessions + users` 校验当前用户
4. API 把上传流写入本机临时文件
5. API 调用 `ingest.IngestLocalFile()`
6. `insertVideo()` 在 `videos` 插入一条记录，初始状态 `uploaded`
7. `buildSourceObjectKey()` 生成原视频 key：`video/{id}/source/{filename}`
8. `UploadRawFile()` 把原视频写入 MinIO `raw-media`
9. `updateVideoSourceObjectKey()` 回写 `videos.source_object_key`
10. `insertTranscodeJob()` 在 `transcode_jobs` 插入一条 `pending` 任务，payload 里带：
    - `videoId`
    - `sourceBucket = raw-media`
    - `sourceObjectKey`
11. `markVideoQueued()` 把 `videos.status` 改成 `queued`
12. API 返回 `201 Created`，包含：
    - `id`
    - `jobId`
    - `status = queued`
13. API 额外调用 `publishVideoUpdated()`，向 SSE 客户端广播一次 `video.updated`
14. 首页 `HomePage` 收到 SSE 后，调用 `refreshFeed()`

### 3.2 Worker 路径

1. worker 主循环调用 `claimPendingJob()`
2. 在事务里挑出最早的一条 `transcode_jobs.status='pending'`
3. 该事务把：
   - `transcode_jobs.status -> running`
   - `videos.status -> processing`
4. worker 调用 `notifyVideoUpdated()`，向 API `/internal/events/video-updated` 发 POST
5. API `handleVideoUpdatedNotification()` 再调用 `publishVideoUpdated()`，首页收到后刷新
6. worker `processJob()` 解析 `payload_json`
7. 从 `raw-media` 下载原视频到本地临时目录
8. `probeVideo()` 用 `ffprobe` 读取时长/宽高
9. `transcodeToHLS()` 用 `ffmpeg` 转成 HLS
10. `generateCover()` 用 `ffmpeg` 生成 `cover.jpg`
11. `uploadHLSDir()` 把：
    - `index.m3u8`
    - `seg_XXX.ts`
    上传到 `vod-media`
12. `UploadImageFile()` 把封面上传到 `image-assets`
13. `markVideoReady()` 更新 `videos`：
    - `status = ready`
    - `play_object_key = video/{id}/hls/index.m3u8`
    - `cover_object_key = video/{id}/cover.jpg`
    - `duration_ms / width / height`
    - `published_at = NOW()`
14. `markJobSuccess()` 更新 `transcode_jobs.status = success`
15. worker 再次调用 `notifyVideoUpdated()`
16. API 再次发 `video.updated`
17. 首页收到后再次 `refreshFeed()`，这次能看到 `ready` 状态和 `playUrl / coverUrl`

### 3.3 API 查询到 Qt 播放路径

1. 首页 `HomePage::fetchFeed()` 请求 `GET /api/videos`
2. API `handleVideos()` 查询 `videos`
3. 同时关联/统计：
   - `users`
   - `video_likes`
   - 如果请求带 token，还会先过 `user_sessions`
4. `toVideoResponse()` 把：
   - `cover_object_key -> coverUrl`
   - `play_object_key -> playUrl`
5. 用户点击卡片
6. `HomePage::requestVideoDetail()` 请求 `GET /api/videos/{id}`
7. API `handleVideoDetail()` + `findVideoByID()` 返回详情
8. `HomePage::handleVideoDetailReply()` 判断：
   - `status == ready`
   - `playUrl` 非空
   否则不允许进入播放
9. 满足条件后，`emit playRequested(playUrl, ...)`
10. `MainWindow::connectPlaybackFlow()` 捕获信号
11. `VideoPlayerWindow::showSelectedVideo()` 调用 `PlayerController::openMedia(playUrl, ...)`
12. `PlayerController::openMediaWithIjkPlayer()` 执行：
    - `ijkPlayer_->setDataSource(playUrl)`
    - `ijkPlayer_->prepareAsync()`
13. `IjkMediaPlayer::prepareAsync()` 进入 `FFPlayer::ffp_prepare_async_l()`
14. `FFPlayer` 内部 `avformat_open_input()` 打开 `http://.../vod/video/{id}/hls/index.m3u8`
15. API `/vod/...` 命中 `handleVODObject()`
16. API 再通过 `OpenVODObject()` 从 MinIO `vod-media` 读取 playlist / ts 分片
17. `http.ServeContent()` 把 m3u8 和 ts 返回给播放器
18. `Prepared` 事件回到 `PlayerController`
19. 当前实现到这里是“已准备可播放”
20. 用户点击播放按钮，`requestPlay()` 才会调用 `ijkPlayer_->start()`
21. 之后进入真正播放

## 3.4 当前实现和“自动播放”之间的差异

如果严格按当前代码：
- 点击视频卡片后，并不会自动 `start()`
- 当前只会 `setDataSource + prepareAsync`
- 等播放器进入 `Prepared`
- 再由用户点击播放按钮触发 `requestPlay()`

所以“API 查询 -> Qt 播放”在当前代码里更准确地说是：
- API 查询 -> Qt 打开并预加载 -> 用户点击播放 -> 真正开始播放

## 4. 5 个最关键函数

## 4.1 `apiServer.handleVideoUpload()`

位置：
- `server/cmd/api/main.go:208`

输入：
- HTTP multipart 请求
- `Authorization: Bearer ...`
- form 字段：`file`、`title`、`desc/description`

输出：
- 成功：`201` JSON，返回 `video id / job id / status`
- 失败：`4xx/5xx`

依赖：
- `requireAuthenticatedUser()`
- 本机临时文件系统
- `ingest.IngestLocalFile()`
- `publishVideoUpdated()`

失败点：
- token 缺失或过期
- multipart 解析失败
- 文件字段缺失
- 临时文件写入失败
- 下游 MySQL / MinIO / ingest 任一失败
- SSE publish 查库失败

为什么关键：
- 它是 Web 上传链路的总入口，决定“上传请求”能否转成“已入队任务”

## 4.2 `ingest.IngestLocalFile()`

位置：
- `server/internal/ingest/ingest.go:31`

输入：
- `ctx`
- `database`
- `minioStorage`
- `localPath`
- `originalFilename`

输出：
- `ingest.Result`

依赖：

- `videos` 表
- `transcode_jobs` 表
- MinIO `raw-media`

失败点：
- 路径解析失败
- 文件不存在/是目录
- `insertVideo()` 失败
- `UploadRawFile()` 失败
- `updateVideoSourceObjectKey()` 失败
- `insertTranscodeJob()` 失败
- `markVideoQueued()` 失败

为什么关键：
- 它把“一个本地文件”变成“数据库记录 + 原片对象 + 待执行任务”
- API 上传和 importer CLI 都复用它

## 5. 最终结论

### 5.1 当前闭环的真实形态

当前上传到播放闭环已经是通的，但真实实现是：
- 上传入队：API 或 importer 调 `ingest.IngestLocalFile()`
- 队列：MySQL `transcode_jobs`
- 转码：worker 轮询抢任务，FFmpeg 产 HLS + 封面
- 存储：MinIO 三个 bucket
- 状态传播：worker 回调 API 内部接口，API 发 SSE，前端刷新 feed
- 播放：Qt 通过 `/api/videos/{id}` 拿 `playUrl`，再经 `/vod/*` 代理到 MinIO `vod-media`

### 5.2 这条链路里最值得记住的几个事实

- 当前没有 Redis；Redis key 为空
- 当前“队列”是 MySQL `transcode_jobs`
- `videos / transcode_jobs` 不是 `server` 运行时代码自动建的，需要先按部署文档建表
- 首页 `/api/videos` 会返回非 ready 状态视频，真正拦截播放的是 `HomePage::handleVideoDetailReply()`
- 当前播放器是“prepare 后等待用户点播放”，不是点击卡片后自动开始播
- API `/vod/*` 和 `/image/*` 实际是 MinIO 代理层，不是本地文件服务
